# ADR-0032: Codex project-scoped hook enforcement (VS Code bridge closure)

## Status

Accepted

## Context

`docs/adr/0029-codex-host-packaging-and-approval-boundary.md` shipped the Codex CLI plugin host and disclosed, explicitly, that the VS Code bridge was only half-built: `install-codex.mjs --target skill` installs the standalone `krylo-run` Skill to the documented user Skill location (`$HOME/.agents/skills/krylo-run/`), giving `$krylo-run` explicit-invocation discoverability in the Codex IDE extension, but that Skill install carries **no hook enforcement** -- the Codex IDE extension does not support plugins at all, so none of KRYLO's plugin-bundled hooks (`hooks/codex-hooks.json`) ever load in a VS Code session. `docs/codex-capability-matrix.md`'s "Documented follow-up" section named this precisely: "Full VS Code project-scoped hook setup... is not implemented this checkpoint."

This ADR closes that gap: explicit, dry-run-first, ownership-safe, reversible `<repo>/.codex/hooks.json` setup, per `docs/process/MULTI_HOST_CODEX_MAINTENANCE_DESIGN.md` Section 10.4.

### Re-verification against the current stable Codex release (not the documented 0.120.0 baseline)

The task's own instruction was explicit: do not assume `codex-cli 0.120.0` (the version every existing KRYLO Codex document was verified against) is still current. Checked directly:

- `gh api repos/openai/codex/releases`: the current stable line is **`rust-v0.152.1`** (published 2026-09-01); `0.153.0-alpha.*` exists but is a pre-release, not the stable line. The installed binary in this environment remains `0.120.0` -- a 32-minor-version gap.
- Fetched `codex-rs/hooks/schema/generated/pre-tool-use.command.input.schema.json` at `rust-v0.152.1` directly: **`tool_name` is now a bare `"type": "string"`, no longer the literal `const "Bash"`** ADR-0029 found and fixed the matcher for on 0.120.0. This is real platform drift, not a documentation error -- Codex now differentiates tool names at PreToolUse (confirmed further by the handler's own test fixtures, which construct requests with `tool_name: "apply_patch"` and `tool_name: "Bash"` as distinct values). KRYLO's existing matcher (`"Bash|shell|exec_command|apply_patch|mcp__.*"`, `codex-hooks.json`) and `risk-gate-codex.mjs`'s `normalizeCodexToolName()` were already written to tolerate exactly this differentiation as a forward-compatible case -- **no code change is required by this finding**, but it is recorded here and in the capability matrix so the "why we kept those extra alternatives" reasoning is evidence-backed rather than speculative.
- Fetched `codex-rs/hooks/src/events/pre_tool_use.rs` at `rust-v0.152.1` directly (the current handler AND its own unit tests, run against the real parser): `permission_decision_deny_blocks_processing` confirms `permissionDecision: "deny"` + `permissionDecisionReason` still blocks correctly -- `emitCodexPreToolDeny()` (`scripts/host/codex/hook-transport.mjs`) remains valid, unchanged, on the current stable release.
- The same source's `unsupported_permission_decision_fails_open` test is a **stronger, more severe finding than ADR-0029 recorded for 0.120.0**: an unsupported `permissionDecision` value (`"ask"`) is asserted to produce `should_block: false` -- i.e. the tool call **proceeds** (fails OPEN), not merely "the hook fails" as ADR-0029's more conservative phrasing implied for 0.120.0. The identical fail-open behavior is confirmed for the legacy `decision: "approve"` field (`deprecated_approve_decision_fails_open`). This makes KRYLO's existing, unchanged design decision -- `risk-gate-codex.mjs`/`hook-transport.mjs` have **no code path capable of emitting `"ask"` or `"approve"`, by construction** -- more clearly load-bearing than previously documented, not less: were that constraint ever violated, the current stable release would silently ALLOW the gated action through, not merely log an error.
- The same source also shows `permissionDecision: "allow"` + `updatedInput` now completing successfully (`permission_decision_allow_can_update_input`), unlike the 0.120.0 finding ADR-0029 recorded (rejected outright). This is genuine drift, but it is **not acted on by this ADR**: ADR-0029's own session-bootstrap mechanism (`user-prompt-submit-codex.mjs`, host-authoritative `UserPromptSubmit`-based) was deliberately redesigned to depend on nothing in this family after the third bootstrap attempt failed; revisiting whether a Claude-parity native "ask" experience is now buildable on `allow`+`updatedInput` is out of scope for this ADR and would itself require its own exact-released-runtime evidence, tests, security review, and ADR reasoning, per the task's own explicit instruction not to change ADR-0029 behavior on drift evidence alone.
- Fetched `codex-rs/hooks/schema/generated/pre-tool-use.command.output.schema.json` at the same tag: `permissionDecision` enum still includes `allow|deny|ask` at the schema level -- schema-valid is still not the same as handler-accepted (the exact distinction ADR-0029 already established for the session-bootstrap history), confirmed again here for a different field.
- Fetched `https://learn.chatgpt.com/docs/hooks` (current, live): confirms `<repo>/.codex/hooks.json` (or inline `<repo>/.codex/config.toml`) as the project-hook location; confirms project-local hooks load only once the project `.codex/` layer is explicitly trusted via `/hooks`, independent of and in addition to plugin-hook trust; confirms `PLUGIN_ROOT`/`PLUGIN_DATA` are **plugin-bundled-hook-only** extensions, never available to a project-scoped hook's `command`/`commandWindows`; confirms Codex resolves a hook-definition path from the **git root**, not the live process `cwd`, for stability. Does not document a `${VAR}`-style templating layer for `command`/`commandWindows` strings themselves (that exists for MCP tool `input` templates only) -- `${PLUGIN_ROOT}`/`%PLUGIN_ROOT%` in the existing plugin-bundled `codex-hooks.json` therefore must be ordinary POSIX/`cmd.exe` shell-native environment-variable expansion performed by whatever shell Codex spawns the command through (consistent with `command` using `${VAR}` syntax and `commandWindows` using `%VAR%` syntax -- the two platforms' own native env-var syntax, not a Codex-invented templating mini-language), not a documented Codex extension for project hooks.

Evidence categories used below match the existing capability matrix's own convention: **locally passed**, **statically inspected**, **configured but not run**, **blocked by platform**.

## Decision

- **No machine-specific absolute path in `<repo>/.codex/hooks.json`.** Because `PLUGIN_ROOT`/`PLUGIN_DATA` are confirmed plugin-only and no portable Codex-native templating exists for project-hook `command` strings, KRYLO does not attempt to reconstruct the plugin-hook pattern (env-var expansion) for project hooks. Instead, per the design doc's own documented fallback (Section 10.4), setup installs a **thin, project-local launcher** at `<repo>/.codex/krylo/launch.mjs`, referenced from `hooks.json` by a plain **project-relative** command path (`node .codex/krylo/launch.mjs <event>`), which Codex resolves from the git root (the one path-resolution guarantee the current docs do confirm). The launcher contains no policy: it locates the real, already-installed KRYLO runtime via the exact same portable, deterministic algorithm `scripts/host/codex/context.mjs` already uses (`path.join(os.homedir(), '.agents', 'skills', 'krylo-run', ...)`, with a `KRYLO_STANDALONE_ROOT` test/override escape hatch mirroring every other KRYLO override convention), then re-executes the real target script (`scripts/security/user-prompt-submit-codex.mjs`, `scripts/security/risk-gate-codex.mjs`, `scripts/runtime/posttool-telemetry-codex.mjs`) from there with the identical stdin/argv/exit-code contract, unchanged. This is a redirector, never a second policy source (design doc Section 5.2's architectural rule): it contains no risk classification, no approval logic, no completion logic.
- **The standalone Skill install now carries a real, functional runtime.** `install-codex.mjs --target skill` is extended to also copy `plugins/krylo/scripts/`, `references/`, `schemas/`, and `policies/` (verbatim, via the same `copyDirRecursive` the Skill copy already uses -- not a second implementation) into the same destination (`$HOME/.agents/skills/krylo-run/`). This is required for the launcher to have anything real to invoke; without it, `--target hooks` alone would wire up enforcement pointing at scripts that do not exist anywhere reachable. `scripts/host/codex/context.mjs`'s existing `resolveCodexPluginRoot()` fallback (`PLUGIN_ROOT_FROM_SOURCE`, computed from `import.meta.url`) already resolves correctly once the scripts physically exist at this new location -- **no code change to `context.mjs` itself was needed**, only to what `install-codex.mjs` copies.
- **New `--target hooks` (and `--target all` now includes it).** `planHooksInstall`/`removeHooks` in `install-codex.mjs` implement:
  1. Inspect the current `<repo>/.codex/hooks.json` (absent, KRYLO-owned, or foreign-but-mergeable) and a KRYLO-owned sidecar `<repo>/.codex/krylo-hooks-meta.json` recording exactly which event-array entries KRYLO previously installed.
  2. Produce a dry-run plan by default; `--apply` required to write.
  3. **Semantic array-level merge, not whole-file replacement**: KRYLO owns exactly one matcher-group entry per event (`UserPromptSubmit`, `PreToolUse`, `PostToolUse`), appended to (or, on a verified upgrade, replaced within) that event's existing array. Any other entry in the same array, or any other event key entirely, is left byte-for-byte untouched -- satisfying design doc Section 10.4's "preserve unrelated user/project hooks" requirement, which the whole-file-replace pattern already used for the Skill/`.rules` installs (dedicated KRYLO-only files with no such concern) does not need to solve.
  4. **Ambiguous-ownership refusal**: if the sidecar records a previously-installed entry that no longer deep-equals what is actually present in the live `hooks.json` (hand-edited or partially removed), setup refuses that event's slot outright (`error: 'ambiguous-ownership'`) rather than guessing whether it is still safe to replace or remove -- consistent with every other KRYLO setup script's "never silently overwrite anything not exactly recognized as KRYLO's own" rule.
  5. **Backup before replace**: a full copy of the pre-existing `hooks.json` is written to `hooks.json.backup-<timestamp>` before any KRYLO-owned entry is replaced (upgrade path only -- a fresh append never needs one, matching the Skill-install convention).
  6. **Uninstall/rollback**: `--remove` deletes only the sidecar-recorded KRYLO entries from `hooks.json` (refusing, per the same ambiguous-ownership rule, if they no longer match) and reports the backup path for manual restore; never deletes the launcher directory or the file itself if foreign content remains.
  7. **Git-tracked reporting, no `.gitignore` mutation**: setup reports whether `<repo>/.codex/hooks.json` is currently git-tracked or untracked (`git ls-files --error-unmatch`, argv array, `shell:false`, matching every other subprocess call in this codebase) and never writes to `.gitignore`.
  8. **`commandWindows` provided for every entry**, using the identical launcher path with Windows path separators, matching the plugin-bundled file's own established `command`/`commandWindows` pairing convention.
- **No `$comment` (or any other non-event key) in the generated project `hooks.json`.** Unlike the plugin-bundled file (which already carries an unverified-if-tolerated `$comment` key -- "configured but not run", never confirmed against a live parse), the newly-generated project file is kept to exactly the three known event keys, since this ADR's own verification pass could not confirm current strict-parsing behavior for unknown top-level keys either way, and the safer, smaller change is simply not to introduce a second instance of an already-flagged-as-unverified risk. Documentation instead lives in `install-codex.mjs`'s own code comments and this ADR.
- **Refusal path preserved exactly as designed.** When the standalone Skill is present (runtime copied) but project hooks are absent, foreign, or ambiguous, KRYLO's own `enforcementNote` (already present on the Skill-install plan) continues to say explicitly that a Skill-only install provides no enforcement; this ADR adds no new autonomous-run downgrade path and does not change the Skill's own instructions to imply otherwise.
- **Hook trust is never bypassed.** Setup writes the hooks file and reports it; it does not attempt to mark it trusted, use `--dangerously-bypass-hook-trust`, or claim the project `.codex/` layer is trusted. The user must review and trust it through Codex's own `/hooks` flow before it fires, exactly as for the plugin-bundled file.

## Consequences

- Closing this gap makes the VS Code bridge genuinely two-sided: a standalone Skill for discoverability, plus project-scoped hooks for the actual `PreToolUse` hard-deny/require-approval-fail-closed/telemetry enforcement boundary, without a second policy implementation anywhere -- the launcher re-executes the exact same `risk-gate-codex.mjs` (and siblings) the plugin path already uses and already has full test coverage for.
- The launcher introduces one new, narrow failure mode not present in the plugin-bundled path: the runtime it delegates to might not exist at all (Skill never installed, or removed after hooks were installed). `PreToolUse`'s launcher fails closed (deny) in that exact case, since it cannot determine whether a run is even active without the real script; `UserPromptSubmit`/`PostToolUse` (non-security-boundary, telemetry/lifecycle only) no-op silently instead, avoiding pure UX noise with no security benefit.
- No change to Shared Core, `risk-policy.mjs`, the plugin-bundled `codex-hooks.json`, or the Claude host. No change to ADR-0029's `require-approval` fail-closed boundary or its session-bootstrap mechanism -- the newly-confirmed `allow`+`updatedInput` behavior on the current stable release is recorded as evidence only, not acted on.
- Live, authenticated confirmation that Codex actually spawns a project-scoped hook's `command` with the process `cwd`/environment this ADR assumes, and that a git-root-relative command path resolves as the current docs describe, remains unexercised in this environment (no authenticated Codex session available) -- recorded as environment-blocked in the capability matrix, not claimed as verified.
