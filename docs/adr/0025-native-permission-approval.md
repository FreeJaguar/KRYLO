# ADR-0025: Native host-controlled permission approval replaces KRYLO-APPROVE

## Status

Accepted

## Context

ADR-0024 introduced `scripts/security/human-approval-gate.mjs`, a `UserPromptSubmit` Hook that scanned a genuine top-level human chat message for an explicit `KRYLO-APPROVE <id>` / `KRYLO-DENY <id>` phrase, as the only path that could transition a risk approval from `pending` to `approved`. That ADR itself states the design's residual limitation plainly: it proves a confirmation phrase was present in a genuine top-level prompt submission, not that a human specifically typed it, and its own "Stated guarantee and residual scope" section says this should be revisited "if a future official Claude Code mechanism provides a stronger, documented human-authorization primitive."

Continuing the security-hardening review of the multi-host Foundation, a further look at official Claude Code documentation and the project's own CHANGELOG found exactly that primitive already exists and is more reliable than believed at the time ADR-0024 was written: `permissionDecision: "ask"` on a PreToolUse Hook puts a human-facing allow/deny prompt directly in Claude Code's own permission UI, at the moment of the actual tool-call attempt — not KRYLO-local state, not a chat-text convention the model could imitate or race, and not a second round-trip (request, wait for a human to type a phrase, retry) the way KRYLO-APPROVE required.

The reason ADR-0024 (and, earlier, `scripts/security/risk-gate.mjs`'s own header comment) did not simply use `ask` in the first place was a documented reliability concern: `anthropics/claude-code#39344` described `permissionDecision: "ask"` being silently overridden by other permission configuration, and this project's pinned compatibility floor (2.1.197, per ADR-0022) predated any fix. That reliability gap is now closed for the specific case KRYLO's risk gate depends on. This project's own verified CHANGELOG (`https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md`, checked in full through the currently released version) states, for v2.1.211:

> Fixed auto mode overriding a PreToolUse hook's `ask` decision for unsandboxed Bash — a hook `ask` now floors the decision at a prompt

This is precisely the failure mode that made `ask` untrustworthy: "auto mode" (a real, commonly used Claude Code permission mode) could previously let a tool call proceed despite a hook saying `ask`, silently defeating the gate. From 2.1.211 onward, a hook's `ask` decision is documented to "floor" (take precedence over) that override — for the Bash tool.

That confirmation is scoped to Bash, and specifically to **"unsandboxed"** Bash — the CHANGELOG entry's own wording, preserved verbatim above and never dropped from any restatement below. The same CHANGELOG was searched in full for an equivalent statement covering PowerShell or any MCP tool's permission dialog, and none was found (see ADR-0026 for the PowerShell-specific consequence of this). Per this checkpoint's instruction not to invent runtime contracts, `ask` is adopted only where it is actually documented, not generalized to every tool or every session mode by assumption. Two further narrowings, both added after independent adversarial review of an earlier draft of this ADR, follow directly from that discipline:

**Disclosed, undetected residual: sandboxed Bash.** `risk-gate.mjs` does not check sandbox state before emitting `ask` for a Bash `git-push`/`git-force` attempt, because there is no evidence the PreToolUse Hook payload exposes it (`code.claude.com/docs/en/hooks` could not be reached from this environment to confirm either way, and no CHANGELOG entry mentions a payload field for it). The v2.1.211 guarantee this ADR relies on is therefore *unconfirmed*, not merely undocumented, for sandboxed Bash specifically — a genuine, accepted gap, not something this ADR claims to have closed. Independent review agreed this is a documentation-accuracy matter, not one requiring a code-level mitigation absent that evidence: adding a check against a payload field that may not exist would itself be inventing a contract. The residual is narrowed by the action-class restriction below (git-push/git-force only) but not eliminated by it.

1. **Permission mode: an allowlist, not a denylist.** The CHANGELOG guarantee is about "auto mode"; it says nothing about `bypassPermissions` (a distinctly-named session mode whose entire documented purpose is skipping permission prompts) or about any other mode. `risk-gate.mjs`'s `ASK_ELIGIBLE_PERMISSION_MODES` accordingly allowlists only the modes actually live-verified below (`auto`, `manual`) rather than denylisting only `bypassPermissions` -- an earlier draft of this check did the latter, and independent security review correctly flagged that as the wrong polarity: it would fail toward the unconfirmed `ask` path whenever `permission_mode` was absent, renamed, or a new upstream mode was introduced, rather than toward the safe `deny`. The risk gate reads `payload.permission_mode` directly off the raw Hook payload (not a normalized identity, which a degraded/session-less identity path can omit -- also independent-review-found and fixed).
2. **Action-class scope.** `classifyRiskAction()` already treated every one of `production-policy.json`'s twelve approval classes identically before this checkpoint — production-deploy, payment, and iam-or-secrets got the exact same handling as a routine `git push` (the policy file's own per-class `decision` field was dead, unread metadata; it has since been removed, see the file's own updated `$comment`). Extending a single-click native prompt to the *most* severe classes uniformly would be a real proportionality regression: the same v2.1.211 CHANGELOG entry that unlocks `ask` also documents that an "always allow" rule chosen at that prompt now "save[s] at the repository root" and "persist[s] across sessions and worktrees" — exactly the kind of standing, unscoped authorization ADR-0019 was written to prevent. Native `ask` is therefore adopted only for `git-push`/`git-force`: common, low-severity, high-frequency, and already the two classes this project's own Skill guidance discusses by name. Every other require-approval class — `production-deploy`, `production-data-write`, `destructive-operation`, `package-publish`, `release`, `merge`, `iam-or-secrets`, `payment`, `external-message`, `external-write` — keeps the deterministic `deny` fail-safe this module used for all of them before this checkpoint, regardless of tool.

Independent review also surfaced that trusting a human-visible `ask` prompt for informed consent requires the prompt to actually reflect the real command, which is a distinct question from whether "auto mode" honors the hook's decision at all. Three further CHANGELOG entries (each verified verbatim against the raw upstream file) are directly relevant to that: v2.1.221 ("Fixed a Bash tool permission-check bypass where zsh could execute hidden commands in `[[ ]]` regex conditionals"), v2.1.223 ("Fixed a Bash permission bypass where a crafted command could hide parts of itself from permission checks"), and, in the same v2.1.223 release, ("Fixed permission prompts so commands padded with tabs or invisible Unicode can no longer hide part of the command from the approval dialog"). ADR-0022's floor is raised to **2.1.223**, not merely 2.1.211, for this reason — see that ADR's Context for the full reasoning and the disclosed limitation that this project's own local environment runs an older CLI (`2.1.197`) than that floor.

A second independent review confirmed both quotes and found the same class of fix continuing in later releases (e.g. v2.1.232's Bash-redirection permission-check fix, v2.1.234's credential-masking-on-relayed-previews fix, v2.1.235's fix ensuring a permission dialog's displayed text and "don't ask again" scope always match what the grant actually covers). This is an actively, continuously hardened area upstream, not a single bug that was fixed once; chasing every subsequent entry would have no natural stopping point. 2.1.223 is retained as a deliberate, disclosed stopping point — the version that closes the specific command-hiding bypass class this ADR's reasoning turns on — rather than the latest version with a relevant fix. Prompt-display-integrity issues above this floor (2.1.223) remain an accepted, disclosed residual risk to the informed-consent premise this ADR relies on, to be revisited if a future review finds a specific fix material enough to justify moving the floor again.

## Decision

- **ADR-0022's pinned Claude Code compatibility floor is raised from 2.1.197 to 2.1.223** (see that ADR for the full version-selection reasoning — 2.1.211 confirms the core auto-mode-override fix; 2.1.223 additionally closes a Bash permission-check bypass directly relevant to the human seeing an accurate command before approving it).
- `scripts/security/risk-gate.mjs`'s `require-approval` handling: for the **Bash** tool, when `decision.actionClass` is `git-push` or `git-force`, and `payload.permission_mode` is in the `ASK_ELIGIBLE_PERMISSION_MODES` allowlist (`auto`, `manual` — see the polarity note above), the decision is `permissionDecision: "ask"`, with a reason describing the action class. Claude Code's own permission UI is where the human actually allows or denies that specific attempt.
- Every other case — PowerShell, MCP tool calls, `bypassPermissions` mode, and every require-approval class other than `git-push`/`git-force` — keeps the deterministic `deny` this module used for every require-approval class before this checkpoint (see ADR-0026 for PowerShell specifically; the same absence-of-evidence reasoning applies to MCP tools and to the excluded classes, none of which were covered by the Bash-scoped, auto-mode-scoped fix either).
- `scripts/security/human-approval-gate.mjs` is deleted. It no longer has a valid non-authority purpose: its entire reason to exist was granting the `approved` transition KRYLO-APPROVE relied on, and no code path consumes that transition to authorize execution any more.
- `scripts/security/risk-policy.mjs`'s `consumeMatchingApproval()` and `isApprovalUsable()` are deleted. They were the only code that ever read a KRYLO-local `riskApprovals` record's `approved` status and used it, by itself, to allow a tool call. Per the explicit security requirement below, that is no longer permitted for any tool, so the function has no remaining legitimate caller.
- `scripts/security/risk-policy.mjs`'s Hook-entrypoint protection list drops `human-approval-gate.mjs` (the file no longer exists; nothing is gained by continuing to name it).
- The `run` Skill's `UserPromptSubmit` Hook registration is removed (`skills/run/SKILL.md`).
- `runtime/update-state.mjs`'s CLI-level `--resolve-approval <id>=approved` remains unconditionally refused, and `--resolve-approval <id>=denied` remains allowed — this is orthogonal to the authorization question (a model backing off its own request was never the concern) and is preserved as-is.
- `riskApprovals`, `--request-approval`, and the `RISK_APPROVAL_REQUIRED` terminal state are **not** removed. They remain legitimate run-level orchestration/audit bookkeeping — a model may still register that a class of action needs human review and pause the run for it — but per the security requirement, no such record is read or consumed by the risk gate to grant execution any more, for any tool.

## Live verification (final Foundation checkpoint)

Everything above this section was justified from CHANGELOG text and unit/integration tests against `risk-gate.mjs` directly (mocked Hook payloads, no real Claude Code process). A later checkpoint obtained a genuine, checksum-verified `2.1.223` binary (npm has not published past `2.1.197`; see ADR-0022's Context for that discovery) and drove it live, end to end, in non-interactive (`-p`) mode with `risk-gate.mjs` wired as a real PreToolUse Hook via `--settings`, against an isolated KRYLO run. This is real evidence, not a description of expected behavior:

- **`--permission-mode manual` (the documented default for an ordinary interactive session), hook returns `ask`**: tool call blocked (`permission_denials` populated, no side effect occurred); the model's own summary explicitly described this as the system "asking you to allow or deny it directly" -- distinct, in its own words, from a flat denial.
- **`--permission-mode auto` (the observed default for a non-interactive `-p` session with no `--permission-mode` flag at all -- a distinct context from `manual`'s interactive default; re-confirmed directly on the pinned 2.1.223 floor binary, not merely the CLI used for the rest of this live pass), hook returns `ask`**: also blocked, same as manual mode. This is the exact, direct, live confirmation of the v2.1.211 CHANGELOG claim this whole design rests on -- not merely a repeated citation of the changelog text.
- **`--permission-mode default` (a sixth value, live-verified on the pinned 2.1.223 floor binary; a second independent review round found the CLI accepts it silently and echoes `"permission_mode":"default"` in the real Hook payload even though it is absent from `claude --help`'s own six-item choices list), hook returns `ask`**: also blocked; the model's own description again read as a request for approval before proceeding ("לפני שאני מנסה שוב, אתה בטוח שאתה רוצה שאני אבצע push"), not a flat denial. Added to `ASK_ELIGIBLE_PERMISSION_MODES` on the strength of this direct evidence -- excluding an undocumented-but-real mode value would have silently made native `ask` inert for whatever real sessions actually reach it, which is exactly the kind of gap the allowlist redesign above was meant to catch, not create.
- **`--permission-mode bypassPermissions`, hook returns `ask`**: also blocked. This was unexpected given this ADR's own conservative design (which falls back to `deny` in `bypassPermissions` specifically because no CHANGELOG entry confirms `ask` there) -- live testing shows the hook's `ask` decision was honored even in this mode, at least in this non-interactive test. **This does not prove the conservative `bypassPermissions` → `deny` fallback is unnecessary**: every test here used `-p` (non-interactive) mode, where there is no human to actually show a prompt to regardless of `permission_mode` -- so `ask` and `deny` are observably equivalent in this specific context (both block, with nobody able to answer). Whether a genuinely interactive session running with `bypassPermissions` would actually surface a live prompt to a present human, or would resolve `ask` to an automatic non-interactive-style deny the same way, was not established one way or the other. The conservative fallback is retained; this finding is recorded as evidence that keeping it costs nothing observable in the one context it could be tested in, not as proof it is safe to remove.
- **A real `git push origin main` attempt through the real `risk-gate.mjs`** (git-push class, Bash, manual mode): blocked, with the model's own description again distinguishing this from a flat denial ("it's asking you to allow or deny it directly (not through me)").
- **A real `git branch -D <name>` attempt** (destructive-operation class, outside the native-ask allowlist): blocked, described by the model as "an automated guard blocking the destructive branch delete" -- language that reads as a flat block, not an interactive prompt, consistent with this class correctly getting `deny` rather than `ask`.
- **A real `Remove-Item -Recurse -Force` attempt through the PowerShell tool**: the tool name in the real Hook payload was confirmed to be exactly `"PowerShell"` (matching `risk-policy.mjs`'s expectation); the destructive delete was blocked, and the model's own summary explicitly said the block "isn't wired to the normal approval prompt for this tool" -- an unprompted, independent confirmation, in the model's own words, that PowerShell correctly gets `deny` rather than `ask` (ADR-0026).
- Attempts to elicit a live test of the sensitive-path (`.env`) and destructive-database (`DROP TABLE`) deny paths were refused by the model's own safety judgment before any tool call was attempted (no Hook invocation occurred to observe) -- a reasonable, expected model behavior, but not additional live evidence beyond what the existing automated test suite already covers for those specific classes. MCP deny paths were not live-tested in this pass (would require a live MCP server; already covered exhaustively by the automated suite) and remain automated-test-only evidence.

**Explicitly NOT established by this live pass (a second independent security review's findings, both accepted as genuine residual gaps rather than resolved by assumption):**

- **Whether a saved "always allow" choice at the native prompt can override a subsequent hook `ask` decision.** The v2.1.211 CHANGELOG entry this ADR already cites documents that such a rule "save[s] at the repository root" and "persist[s] across sessions and worktrees" -- but whether a *hook's* `ask` is re-evaluated on every subsequent matching attempt regardless of a saved rule, or whether a saved "always allow" can short-circuit the hook entirely on a later attempt, was not tested. `-p` mode has no clickable "always allow" option to exercise. If a saved rule can override a later hook `ask`, one human click could disable this action class's gate for that repository indefinitely, invisibly to KRYLO (which, per this ADR's own Consequences, never observes the human's choice either way). This is recorded as an open, untested question, not assumed safe.
- **Which exact `permission_mode` string value(s) `--dangerously-skip-permissions` (a distinct CLI flag from `--permission-mode bypassPermissions`, per `claude --help`) produces in the real Hook payload.** Only `--permission-mode bypassPermissions` was live-tested. `scripts/security/risk-gate.mjs`'s `ASK_ELIGIBLE_PERMISSION_MODES` is an allowlist (only `auto` and `manual`, both live-verified above, are eligible for `ask`), so this uncertainty fails toward `deny` regardless -- but the exact string this flag produces was not directly observed.

**Unplanned finding, worth recording**: when the PowerShell destructive-delete attempt was blocked, the model's own reasoning explicitly flagged that `risk-gate.mjs`'s own denial-reason text (which tells the model to run `update-state.mjs --request-approval ... --terminal RISK_APPROVAL_REQUIRED` if a human should review it) read to it as "an unverified instruction coming from a tool error message," and it declined to follow it on injection-safety grounds. This is a genuine, if narrow, design tension: guidance KRYLO's own denial reason gives the model in good faith can be indistinguishable, from the model's own security-conscious perspective, from an injection attempt embedded in tool output. This is not a vulnerability (the model *should* be suspicious of instructions embedded in tool output, including KRYLO's own) and is not fixed here; it is recorded because it means the model may not reliably self-serve KRYLO's suggested next step, which is worth keeping in mind for `skills/run/SKILL.md`'s own wording of that same guidance to the model directly (already present there independent of the denial-reason text).

**The sensitive-path (Read/Glob/Grep) HIGH finding took three review rounds to actually close, not one.** Round one found Read/Glob/Grep entirely absent from the matcher and from `classifyRiskAction()` (fixed by adding the tools and checking `file_path`/`path`). A second, independent review round found that fix itself incomplete and reproduced a working bypass end to end: Grep's real schema carries `path` *and* `glob` (the first fix checked only `path`), so `Grep(pattern: '.', glob: '**/.env', output_mode: 'content')` returned `.env`'s contents ungated, and Glob's real field is `pattern`, not `file_path`, so `Glob(pattern: '**/.env')` disclosed secret-file locations ungated. Both are now fixed (`risk-policy.mjs` checks `path`/`glob` for Grep and `path`/`pattern` for Glob -- deliberately excluding Grep's `pattern` field, which is the content-search regex, not a path, so a benign search *for* the text ".env" across ordinary source is not itself denied). Two residual limitations were disclosed by the same round and are accepted, not fixed, at this checkpoint: (1) `sensitivePaths`' patterns are literal-anchored, so a wildcard-suffixed target (`.env*`, `*.env`) evades on every tool including the pre-existing Bash path (`cat .env*` was already unguarded before this checkpoint); this is the same "best-effort text matching" limitation already documented for `touchesDataRoot()` and the Hook-entrypoint check, not something newly introduced here. (2) Content-based secret detection (a Grep search whose *pattern* looks like a secret name, e.g. `AWS_SECRET_ACCESS_KEY`, against arbitrary non-sensitive-path files) is out of scope for a sensitive-*path* control and was never part of this finding's original claim; disclosed here only so it is not mistaken for a gap in the fix above.

**Lower-priority findings from the same security review, deliberately deferred (not blocking, per the reviewer's own framing) but disclosed here rather than silently dropped:**

- **The `git-push` pattern (`\bgit\b[^|;&\n]*?\bpush\b`) is broader than an actual push, and broader than this ADR first disclosed.** `firstMatchingClass()` (`risk-policy.mjs`) normalizes all whitespace, including newlines, to a single space *before* matching, so the pattern's `[^|;&\n]` exclusion is effectively `[^|;&]` in practice -- a newline is not a boundary either. The pattern matches any Bash/PowerShell command where the literal word "push" appears anywhere after "git" without an intervening pipe/semicolon/ampersand (a literal newline included) -- for example `git commit -m "push button feature"`, or a multi-line script containing `git status` on one line and `echo push` on a later one -- not only a real `git push`. Both forms independently reproduced by a third review round. Combined with the still-open "does a saved always-allow persist past this one attempt" question above, an over-broad match means more frequent, sometimes spurious, native `ask` prompts for this class, which could condition a human toward reflexively approving (or "always allow"-ing) them, weakening the gate's practical effect for a genuine push later.
- **The `destructive-operation` delete patterns' relative-path gap is real, but narrower than this ADR first disclosed: it is specific to the literal `rm` pattern, not the PowerShell cmdlet/alias pattern.** A third review round corrected this. Only the Bash/PowerShell-shared `rm` pattern (`\brm\s+(-[a-z]*[rf][a-z]*\s+)+(/|~|\$HOME|[a-z]:\\)`) requires an absolute-path or home-relative target immediately after its flags -- `rm -rf ./build`, `rm -rf node_modules`, and `rm -rf *` all match neither this pattern nor any other, and pass through `destructive-operation` completely ungated (confirmed independently by two review rounds). The PowerShell cmdlet/alias pattern (`\b(remove-item|ri|rd|rmdir|del|erase)\b[^|;&\n]*?(-r\w*|-f\w*|/s\b|/q\b|/f\b)`) has **no path anchor at all** and was independently confirmed to already catch a relative target: `Remove-Item -Recurse -Force build`, `Remove-Item -Recurse -Force ./build`, `ri -Recurse -Force ./build`, and `del /s /q build` all correctly classify as `destructive-operation` today. So the residual gap is exactly: the literal `rm` token (whether invoked directly on a Unix shell or as PowerShell's `rm` alias) with a *relative* target, on either shell -- not PowerShell deletes in general, and not the `rm` alias specifically (PowerShell's `rm` alias with an *absolute* target, e.g. `rm -Recurse -Force ~`, was separately confirmed to already match the `rm` pattern, since its flag-shape regex accepts word-style flags too).

## Security requirements (verbatim, preserved)

- Human approval authority must belong to Claude Code's native permission UI, not mutable KRYLO local state or user prompt text.
- KRYLO local approval records may remain for audit/state purposes only if they cannot independently authorize execution.
- Preserve scoped, single-use, run/project/target-bound semantics where still applicable (ADR-0019's schema is unchanged; see its updated "Superseded by").
- Risk gates fail safe (every tool this ADR does not confirm `ask` for keeps `deny`).
- Ordinary non-KRYLO sessions remain unaffected (the Hook is still Skill-scoped, ADR-0021; nothing here changes when it runs).
- No weakening of tests or security checks: `tests/hooks/risk-gate-approvals.test.mjs` and `tests/unit/state-migrations.test.mjs`'s migration-race test were rewritten to prove the *opposite* invariant of before — a persisted, matching, unconsumed `approved` record must still never authorize the action.

## Consequences

- A require-approval `git-push`/`git-force` Bash action is now a single, synchronous interaction: the model attempts it, the human is prompted immediately by the host, and the outcome is immediate — no separate `--request-approval`, no out-of-band chat phrase, no retry.
- Every other require-approval action (PowerShell, MCP, `bypassPermissions` mode, or any class other than git-push/git-force), once denied, has no in-run "unlock" path any more for that same attempt (the old approval-consumption mechanism that could unblock a retry is gone for every tool and class, not just the ones excluded here) — the model must either find an eligible Bash path, or the human must act outside the run via `--request-approval`/`RISK_APPROVAL_REQUIRED`. On a Windows host without Git Bash installed, Claude Code may use PowerShell as its primary or only shell tool, in which case every gated class is effectively an unconditional `deny` with no Bash fallback available at all — this is a real, disclosed platform limitation, not a hypothetical edge case, and it is safer (never a bypass) but less ergonomic than the pre-checkpoint design on that platform. This is a deliberate, documented narrowing in exchange for never letting a KRYLO-local record authorize execution or letting a single-click prompt carry disproportionate weight; it is expected to be revisited once official documentation confirms the same guarantees for those tool types and classes (ADR-0026).
- A human's actual choice at the native prompt (allow or deny) is **not observable by KRYLO at all**, in telemetry or in run state: the risk gate records `status: 'ask'` (that a prompt was issued) at the moment of the attempt and then exits; it is never told what the human subsequently chose. This is a deliberate consequence of moving authorization out of KRYLO's own process into the host's UI. `completionEval()` therefore has no state-level signal either way for this path -- consistent with (not a new regression from) how every outright-`deny` category (sensitive-path, data-root, ...) already worked, where KRYLO likewise never learns whether the model tried and gave up versus never attempted at all.
- No KRYLO product version change (`kryloVersion` unchanged at 0.1.1 per this checkpoint's explicit instruction).
- ADR-0022 is amended (compatibility floor 2.1.197 → 2.1.223); `.github/workflows/validate-plugin.yml`, `.github/workflows/release.yml`, `RELEASE_READINESS.md`, and `docs/17-distribution-and-release.md` are updated to match. `RELEASE_READINESS.md` discloses that this environment's actually-installed CLI (`2.1.197`) is below that floor.
