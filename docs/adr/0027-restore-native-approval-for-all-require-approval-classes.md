# ADR-0027: Restore native ask for every require-approval class, tool, and MCP operation

## Status

Accepted

## Context

ADR-0025 replaced the KRYLO-APPROVE chat-phrase mechanism with Claude Code's native `permissionDecision: "ask"`, but narrowed it to the Bash tool's `git-push`/`git-force` classes only, reasoning that (a) the only version-pinned official confirmation of a hook's `ask` decision actually flooring the permission prompt (v2.1.211's CHANGELOG entry) was scoped explicitly to "unsandboxed Bash" and "auto mode", and (b) extending a single-click native prompt uniformly to every `require-approval` class -- some of them far more severe than a routine push -- would be a proportionality regression versus the heavier `--request-approval`/`RISK_APPROVAL_REQUIRED` human-review path. Every other class, and PowerShell/MCP entirely, kept the deterministic `deny` fail-safe. ADR-0026 (PowerShell classification parity) explicitly anticipated this would need revisiting: "If official Claude Code documentation later confirms the same auto-mode-`ask`-flooring guarantee for PowerShell, `risk-gate.mjs`'s tool-name/action-class check should be extended (and this ADR superseded) rather than silently widened without an equivalent evidence trail."

This narrowing was found to violate KRYLO's own product contract: **if KRYLO policy classifies an action as `require-approval`, there must be a real host-native human-approval path for it.** A `require-approval` classification that always resolves to a deterministic `deny` -- with no in-run path to a human decision at all -- is, in practice, indistinguishable from a true `deny`. `production-deploy`, `payment`, `iam-or-secrets`, and the other nine classes were never actually "gated pending human approval" under ADR-0025's design; they were unconditionally blocked, silently defeating the distinction `production-policy.json` itself draws between `deny` and `require-approval`.

A fresh, targeted verification pass against current official Claude Code documentation (`code.claude.com/docs/en/hooks`, `code.claude.com/docs/en/permissions`) found:

- `permissionDecision` has exactly three **documented** values -- `"allow"`, `"deny"`, `"ask"` -- plus a fourth, `"defer"`, which exists in the runtime (added v2.1.89, precedence `deny > defer > ask > allow` per a still-open documentation-bug issue) but is not part of KRYLO's design surface here and is not used.
- The permissions documentation states plainly that **"PreToolUse hooks run before the permission prompt, for every tool"** except `EndConversation`. This is a general statement about the hook-to-permission-prompt pipeline, not a Bash-specific one.
- The only version-pinned CHANGELOG confirmation remains the v2.1.211 entry, and it remains scoped to Bash and "auto mode" in its own wording.

Read together, this means ADR-0025's original reasoning conflated two different things: "the only specific *bug fix* we can cite by version number happens to be about Bash" is not the same claim as "`ask` is unconfirmed or unreliable for every other tool." The generic mechanism (`permissionDecision`) is documented to apply uniformly across the whole PreToolUse hook contract, for every tool type; the v2.1.211 entry is evidence that one specific override bug in one specific mode was fixed, not evidence that the mechanism itself is Bash-only. Combined with this checkpoint's own prior live testing (ADR-0025's verification log) that already confirmed a PowerShell `deny` decision is honored exactly like a Bash one through the identical Hook JSON output shape, there is no principled basis left for withholding `ask` from PowerShell while granting it to Bash -- both go through the same `hookSpecificOutput.permissionDecision` field, dispatched by the same host pipeline.

The "single-click prompt is disproportionate for severe classes" concern from ADR-0025 is real but is answered differently now: it is a reason to be honest with the user about what the native prompt *is* (a single, immediate, host-UI decision -- not KRYLO's own deliberate `--request-approval` review path) and to keep the still-open "does a saved always-allow persist" question (ADR-0025) prominently disclosed, not a reason to make an entire class of KRYLO's own policy decisions functionally indistinguishable from `deny`.

A related, narrower design question surfaced while implementing this: `classifyMcpTool()` (`scripts/security/mcp-classifier.mjs`) returned the *same* shape -- `{ className, reason }`, wrapped into `{ action: 'require-approval', ... }` by `risk-policy.mjs` -- for both (a) a known, catalogued server's write-shaped operation, and (b) an entirely unrecognized or explicitly-blocked server. Once MCP tools became ask-eligible, this would have silently downgraded "we have never reviewed this server at all" to the same single-click native prompt as "GitHub, a server we know, wants to merge a PR" -- a real regression, since a human has no server identity to meaningfully evaluate in the former case.

## Decision

- `scripts/security/risk-gate.mjs`'s native-ask eligibility check is no longer scoped to `git-push`/`git-force` on Bash only. Every `require-approval` classification -- all twelve classes in `production-policy.json` (`production-deploy`, `production-data-write`, `destructive-operation`, `package-publish`, `release`, `git-push`, `git-force`, `merge`, `iam-or-secrets`, `payment`, `external-message`, `external-write`) and every genuinely-identified MCP write class -- is eligible for `permissionDecision: "ask"`, on the Bash, PowerShell, and MCP tool surfaces (the only three that can ever produce a `require-approval` classification; `risk-policy.mjs`'s Write/Edit/NotebookEdit/Read/Glob/Grep branches only ever produce `deny` or `pass`). No class-based allowlist remains in `risk-gate.mjs`: there is nothing left to enumerate, so no future class can be "accidentally unreachable" by omission from a second list.
- The permission-mode allowlist (`ASK_ELIGIBLE_PERMISSION_MODES = new Set(['auto', 'manual', 'default'])`, ADR-0025) is **unchanged**. `bypassPermissions`, `plan`, `acceptEdits`, `dontAsk`, an absent field, or any future/renamed mode still falls through to the deterministic `deny` fail-safe, for every class and every tool -- widening the class/tool scope does not touch the permission-mode fail-safe at all.
- `mcp-classifier.mjs`'s `classifyMcpTool()` now returns `hardDeny: true` for a malformed tool-name shape, a catalog-blocked server, and an unrecognized server. `risk-policy.mjs`'s MCP branch translates a `hardDeny` result into `{ action: 'deny', ... }` instead of `require-approval`, so these three cases remain a deterministic `deny` regardless of tool eligibility or permission mode -- a genuinely unreviewed or blocked MCP server is never routed through the native ask prompt just because MCP write classes generally are now.
- Sensitive-path protection, KRYLO data-root protection, Hook-entrypoint-invocation protection, and the oversized-command cap are `deny` classifications, not `require-approval`, and are completely unaffected by this ADR -- they never reach the ask-eligibility check at all. This ADR does not weaken any of them.
- `docs/adr/0026-powershell-risk-parity.md`'s Decision bullet describing the "gating outcome is not identical" split (Bash `ask`, PowerShell always `deny`) is superseded by this ADR: gating outcome is now identical to classification outcome for Bash and PowerShell alike. ADR-0026's classification-parity decision itself (the shared `toolName === 'Bash' || toolName === 'PowerShell'` branches, the destructive-delete pattern work) is unchanged and remains in force.

## Consequences

- Every `require-approval` action now has a real, immediate, host-native human-approval path, for every class and for Bash/PowerShell/MCP alike -- KRYLO's product contract ("if policy says require-approval, there must be a real approval path") now actually holds, closing the gap ADR-0025 left open for eleven of twelve classes and two of three tool surfaces.
- The residual, still-open question from ADR-0025 -- whether a saved native "always allow" choice can silently override a future hook `ask` decision for the same repository -- now applies to every require-approval class, not only `git-push`/`git-force`. This makes that open question meaningfully more consequential than it was under the narrower design, and it remains untested (no interactive session was available to exercise a saved-rule click). It is carried forward here as an explicitly heightened, disclosed risk, not resolved.
- The Windows/PowerShell-only-shell platform limitation ADR-0025 disclosed (every gated class becomes an unconditional `deny` with no in-run human path, since Claude Code may have no Bash tool available at all) is resolved by this ADR: PowerShell now has the identical ask path Bash does, so that platform limitation no longer applies.
- An entirely unreviewed or explicitly-blocked MCP server continues to have no in-run resolution path (hard `deny`, same as before this ADR) -- only a *known* server's write-shaped operation gains the native ask path. This is a deliberate, narrower grant than "every MCP require-approval classification," corresponding exactly to which cases have an identity a human could meaningfully evaluate.
- No KRYLO product version change (`kryloVersion` unchanged at 0.1.1, per this checkpoint's explicit instruction).
- `scripts/security/mcp-classifier.mjs` and `scripts/security/risk-policy.mjs` gain a `hardDeny` field/branch; this is additive to the classifier's return shape and does not change any existing caller's handling of the non-`hardDeny` case.

## Supersedes

`docs/adr/0025-native-permission-approval.md`'s class/tool narrowing (the "native ask ONLY for Bash git-push/git-force" decision and its proportionality rationale) and `docs/adr/0026-powershell-risk-parity.md`'s "gating outcome is not identical" Decision bullet. Both ADRs' remaining content (the core native-approval mechanism, the permission-mode allowlist, and PowerShell classification parity) stays in force and is left unedited as an accurate historical record of the reasoning that applied before this ADR.
