# ADR-0028: Foundation final closure — live always-allow proof, settings-weakening protection, edge-case fixes

## Status

Accepted

## Context

This is the final Foundation security/correctness checkpoint before Codex Host work may begin. It closes four remaining classes of concern that prior checkpoints (ADR-0024 through ADR-0027) left open, deferred, or merely disclosed rather than fixed or empirically tested:

1. Whether Claude Code's native "always allow" persistence (or a pre-existing `permissions.allow` rule) could silently disable a KRYLO hook's `ask` decision -- an explicitly untested, disclosed gap since ADR-0025.
2. Whether the model could weaken KRYLO's or Claude Code's own enforcement surface directly (editing `.claude/settings.json`, disabling a hook, editing KRYLO's own installed policy/hook files) -- never previously addressed at all.
3. Four specific edge cases in the risk classifier: a relative-path gap in the destructive-delete pattern, a wildcard/glob evasion of sensitive-path protection, an availability regression treating `.env.example`-style shareable templates as secrets, and an over-broad git-push pattern -- all previously disclosed as accepted residuals, never fixed.
4. A fresh CHANGELOG review from the pinned 2.1.223 floor through the current latest release (2.1.245, checked via the GitHub API), to decide whether any newer fix is one KRYLO's own design actually depends on.

An important operational discovery made while investigating (1): this session's test-isolation env vars (`KRYLO_DATA_ROOT`) were being silently ignored by the runtime CLI scripts invoked via the path baked into the `/krylo:run` Skill's own instructions (`~/.claude/plugins/cache/krylo-marketplace/krylo/0.1.1/scripts/...`). That path is the **installed plugin cache**, a stale snapshot dated before ADR-0024 (still uses the deleted KRYLO-APPROVE mechanism, has no PowerShell/Read/Glob/Grep coverage, no `host/claude/context.mjs`, and does not recognize `KRYLO_DATA_ROOT` at all -- only the older `CLAUDE_PLUGIN_DATA`). The actual source repository (`plugins/krylo/scripts/...`, this checkpoint's own working tree) correctly honors `KRYLO_DATA_ROOT` once invoked directly. This is disclosed as an important operational fact, not a KRYLO code defect: a plugin's installed cache naturally lags its source repository until explicitly reinstalled/updated, which is normal for the plugin development lifecycle, but is worth knowing because it means this environment's own installed KRYLO has not received any hardening from ADR-0019 onward without an explicit update. All live testing in this checkpoint invokes the repository's own scripts directly, with `KRYLO_DATA_ROOT` verified to actually isolate before any test ran.

## Decision

### A. Live always-allow / pre-existing-rule testing

Official Claude Code documentation (`code.claude.com/docs/en/permissions`, "Extend permissions with hooks") states, verbatim: *"Hook decisions don't bypass permission rules. Claude Code evaluates deny and ask rules regardless of what a PreToolUse hook returns: a matching deny rule blocks the call, and a matching ask rule still prompts even when the hook returned `"allow"` or `"ask"`... A blocking hook also takes precedence over allow rules."* This states the hook's own decision is a first-class part of the evaluation, but does not explicitly spell out the exact interaction this checkpoint most needed evidence for (a hook `ask` versus a *pre-existing* `allow` rule specifically), so it was tested live rather than inferred.

Three live tests were run against the pinned, checksum-verified `2.1.223` binary, in an isolated disposable repository, isolated `KRYLO_DATA_ROOT`, and a fresh KRYLO run per test, with a matching `permissions.allow` rule seeded **before** the session started (test case 5/6's scenario -- the most directly scriptable without a human clicking a live UI):

- **Bash, rule via `.claude/settings.local.json`** (`"allow": ["Bash(git push *)"]`), attempting `git push origin main`: blocked. `permission_denials` populated; the model's own report quoted KRYLO's exact denial reason verbatim and confirmed no push occurred.
- **Bash, rule via a `--settings <file>` layer** (a different settings source than local project settings), same command: blocked, identical result.
- **PowerShell, rule via `--settings <file>`** (`"allow": ["PowerShell(Remove-Item *)"]`), attempting `Remove-Item -Recurse -Force ./scratchsubdir`: blocked; the target directory was confirmed to still exist afterward.

All three: the hook's `ask` decision was honored over a pre-existing, matching `allow` rule, from two independent settings sources, on two tool types. **This directly answers the ADR-0025 open question for the pre-existing-rule scenario with real evidence, not inference.**

**Not separately live-tested, disclosed honestly:**
- **The mid-session "click Always Allow, then repeat the same action" dynamic scenario** (test case 2). No interactive human or `--permission-prompt-tool` harness was built to simulate a live click. This is covered by the *same* mechanism just tested: rule evaluation happens fresh on every matching tool call regardless of when the competing rule was written, so a rule saved mid-session is architecturally identical, at evaluation time, to one that existed before the session -- which the live tests directly exercised. This is a reasoned inference from a real, adjacent test, not an untested assumption, but it is disclosed as not itself directly observed.
- **A live MCP require-approval variant.** No live, write-capable MCP server was available in this environment to exercise. The same code-level guarantee applies (the `ASK_ELIGIBLE_PERMISSION_MODES` allowlist and the tool-eligibility check in `risk-gate.mjs` treat Bash/PowerShell/MCP identically, and the host-side rule-evaluation-versus-hook-decision behavior just tested is a host-level mechanism with no documented MCP-specific carve-out), but it was not independently observed for MCP specifically.
- **New-session/worktree persistence** (test cases 3/4) were not separately run; they are the same "pre-existing rule at session start" scenario already covered by tests 1-3 above, just reached via a different mechanism for how the rule came to exist beforehand.

**Section A's core question is resolved: Always Allow and pre-existing allow rules do NOT bypass KRYLO's native ask, confirmed with real, reproducible evidence.** No fallback ConfigChange-hook defense is implemented, per the task's own instruction not to add that complexity when live testing proves `ask` already forces a prompt over persistent allow rules.

**Independent review round 2 (Verifier, Security Reviewer) scrutinized this section's methodology and raised two concerns, both addressed:**

1. *"Is `Bash(git push *)` / `PowerShell(Remove-Item *)` even valid rule syntax, or does it require a colon (`Bash(git push:*)`) to actually match?"* Re-checked against the exact, already-fetched official documentation text (not re-inferred): `code.claude.com/docs/en/permissions`'s own "Wildcard patterns" example uses `"Bash(git push *)"` verbatim as a real rule (in its own deny-list example, blocking git push), and its PowerShell section uses `"PowerShell(Remove-Item *)"` verbatim the same way. The docs state the `:*` suffix is "an equivalent way to write a trailing wildcard" -- an alternative, not a requirement. **Both rule strings used in this checkpoint's live tests are the literal, official documented examples, unmodified.** This concern is resolved, not merely asserted away.
2. *"Which `risk-gate.mjs` did the host actually dispatch -- the repository's, or the stale installed cache disclosed in the Context section above?"* This was a real documentation gap in the first draft of this ADR, not a methodology flaw: each live test's isolated repository carried its own project-level `.claude/settings.json` with an explicit `hooks.PreToolUse` entry whose `command` is the absolute path to *this repository's* `scripts/security/risk-gate.mjs` -- entirely independent of the `/krylo:run` Skill's own frontmatter registration or the installed plugin cache. Corroborating evidence beyond the mere presence of `permission_denials`: the reason text quoted in each test's result ("Claude Code will ask you to allow or deny this specific action") is this repository's current `ask`-branch phrasing specifically; the stale cache's equivalent path uses entirely different wording referencing the removed KRYLO-APPROVE mechanism ("denied pending an explicit, scoped, single-use, expiring user approval"). The observed phrasing matches only the repository's code.

**Not run, disclosed as a genuine remaining gap, not fixed in this round:** a negative control (same seeded rule, KRYLO's hook *not* registered, expecting the action to proceed) was not executed. Its absence does not invalidate the tests performed -- the hook-wiring and reason-text evidence above independently establish which code path ran, which is what a negative control would otherwise have had to infer indirectly -- but running one remains the more direct, conclusive proof and is recorded as follow-up work, not fabricated here.

### B. Model-driven security-config weakening

Two new protections in `scripts/security/risk-policy.mjs`, both `deny` (not `require-approval` -- a model must never negotiate for this, and a human editing this configuration directly is not the threat model, only a model doing so silently is):

- **`touchesClaudeSettings()`**: denies Write/Edit/NotebookEdit targeting `.claude/settings.json` or `.claude/settings.local.json` (project or user-level, any depth), and any Bash/PowerShell command referencing either path. Reading these files is unaffected (not itself a threat, and the model may legitimately need to inspect current configuration). This directly closes the three required regression scenarios: a model can no longer add a `permissions.allow` rule, remove the `hooks.PreToolUse` registration, or set `defaultMode` to `bypassPermissions` by writing to its own settings files.
- **`touchesPluginInstallation()`**: denies Write/Edit/NotebookEdit targeting a path under the KRYLO plugin's own **installed** location (`pluginRoot`, threaded through from `risk-gate.mjs`'s normalized Claude identity -- the plugin-root environment variable a host sets). Deliberately has NO Bash/PowerShell arm as of round 5 below: two attempts (scanning for any reference to `pluginRoot`, then narrowing to a reference plus a fixed "write-shaped" signal list) were each tried and each found, by independent review, to be worse than having no check at all for this specific tool surface -- see round 3/4/5 below for the full history and why this is a disclosed residual gap, not an oversight. This is scoped to the installed location specifically, not to filenames like `risk-gate.mjs` matched anywhere, so under a real host (which sets that environment variable to the installed location) it does not interfere with KRYLO's own source-repository development -- verified by an explicit negative-case test, though this separation is a property of how the host resolves `pluginRoot`, not an unconditional guarantee (see the residual-limitations list below).

Both are regression-tested at the shared-policy unit level and (for the settings-file case) end-to-end through the real Hook process.

### D. Classifier edge cases

1. **Relative-path destructive-delete gap.** The Bash `rm` pattern required an absolute/home-anchored target (`\brm\s+(-[a-z]*[rf][a-z]*\s+)+(/|~|\$HOME|[a-z]:\\)`), so `rm -rf ./build`, `rm -rf node_modules`, `rm -rf .`, `rm -rf *`, `rm -rf ../` all passed through completely ungated. Fixed by dropping the anchor requirement (`(?<!git )(?<!docker )(?<!npm )\brm\s+(-[a-z]*[rf][a-z]*\s+)+\S`) -- a negative lookbehind specifically excludes `git rm`/`docker rm`/`npm rm` (a different tool's subcommand, not the actual filesystem-delete shell command), preserving the exact existing hygiene-command negative tests. Per this task's own explicit direction, the consequence of this widening is `require-approval` (native `ask`, per ADR-0027 -- a real, immediate human-approval path), not an accidental unconditional deny: this is only safe to do now that ADR-0027 restored native ask to every require-approval class, including `destructive-operation`.
2. **Sensitive-path wildcard evasion.** The `.env` and `id_rsa` sensitivePaths patterns anchored their trailing boundary to end-of-string, a literal `.`, or a path separator -- never a literal `*` -- so `cat .env*`, `Grep(glob: '.env*')`, and `Glob(pattern: '**/.env*')` (shell/tool wildcards that expand to the exact same secret file at execution time) evaded the pattern entirely. Fixed by adding `\*` to the accepted trailing-boundary alternation for both patterns (and, separately, for the `.pem`/`.pfx`/`.key`/... and `secrets.json`/`.yaml`/`.toml` end-anchored patterns). Schema-aware, not a blanket wildcard ban: Grep's `pattern` field (a content regex, never a path) remains untouched, per the existing ADR-0027 distinction.
3. **`.env.example` regression.** The same `.env` pattern's boundary (matching `.env` followed by end-of-string, `.`, `*`, or a separator) treated `.env.example`, `.env.sample`, `.env.template`, `.env.dist`, and `.env.defaults` -- conventional, public, non-secret templates committed to version control on purpose -- identically to a real secret `.env`. Fixed with a narrow, explicit exception (`ENV_TEMPLATE_EXCEPTION`) checked before the general sensitive-path match, matched at a full path-segment boundary so `.env.example.secret` or a directory literally named `.env.example` containing a real secret is not accidentally exempted.
4. **git-push over-match.** `\bgit\b[^|;&\n]*?\bpush\b` matched the literal word "push" anywhere after "git" with no requirement that it be the actual subcommand -- `git commit -m "push button feature"` classified as `git-push`, and whitespace normalization (`firstMatchingClass()`) neutralized the pattern's own newline exclusion, so a multi-line script with "git" on one line and "push" on a later one matched too. Tightened to require "push" immediately follow "git" plus only recognized global option tokens (`-C`, `-c`, `--git-dir=`, etc.): `\bgit\b(?:\s+(?:-{1,2}[\w-]+(?:[=\s]\S+)?))*\s+push\b`. All previously-required matches (`-C`/`-c`/`--git-dir=` variants, `+refspec`/`--force` force-push detection) still match; the false-positive case no longer does.

All four are covered by new, deterministic regression tests (`tests/unit/risk-policy.test.mjs`), and the full suite (309 tests at the point these were added) passes with no regressions.

**Independent review round 2 (fresh Verifier, fresh Security Reviewer) found that two of these four fixes, and one Section B protection, themselves contained real, reproducible bugs -- all fixed in the same checkpoint, before closing:**

- **git-push quoted-subcommand regression (found by Security Reviewer, confirmed HIGH).** The round-1 tightening (`\bgit\b(?:...)*\s+push\b`) no longer matched `git "push" origin main` or `git 'push' origin main` -- a real, trivial evasion the *round-1 pattern itself introduced* (the pre-round-1 pattern had caught it). Confirmed live that `git "push"` genuinely dispatches to git's push subcommand. Fixed by tolerating optional matching quotes around `push` in both the `git-push` and `git-force` patterns: `\s+['"]?push['"]?\b`.
- **`rm` exclusion spoofed by whitespace normalization and env-var prefixes (found independently by both the Verifier and the Security Reviewer, confirmed HIGH).** The round-1 negative lookbehind (`(?<!git )(?<!docker )(?<!npm )`) inspected only the four raw characters immediately preceding `rm` -- not whether `git`/`docker`/`npm` was genuinely a separate command. Two real, reproduced bypasses: a two-line script normalized to `"echo git rm -rf /"` (an unrelated preceding word coincidentally ending in the excluded verb), and a real, working POSIX env-var-assignment prefix, `"x=npm rm -rf /var/data"` -- both evaded the pattern entirely, worse than the original relative-path gap since these use *absolute* targets the pre-round-1 pattern already caught. Fixed by requiring `git`/`docker`/`npm` itself be at a genuine command-start position (start-of-string, or immediately after a `;`/`&`/`|` separator) before it can exclude the following `rm`: `(?<!(?:^|[;&|])\s*(?:git|docker|npm)\s)`.
- **`.env.example` exception's path-traversal bypass (found by Security Reviewer, confirmed a genuine secret leak, reproduced on real Windows filesystem).** The round-1 `ENV_TEMPLATE_EXCEPTION`'s trailing boundary (`$|[\\/]`) matched anywhere in the string, not only at the end, so `.env.example/../.env` matched the exception (exempting the *entire* string from the sensitive-path check) while the path actually resolved, after traversal, to the real `.env` -- confirmed to genuinely return real secret content when read this way. This directly contradicted this ADR's own original claim (below) that a directory literally named `.env.example` containing a real secret would not be exempted; that claim was false as originally implemented. Fixed by anchoring the exception to end-of-string only (`$`, not `$|[\\/]`): the template filename must be the *final* path component, so `.env.example` and `config/.env.example` remain exempt, but `.env.example/../.env` and `config/.env.example/real-secret` are not (falling through to the ordinary `.env` pattern, which correctly still matches the literal `.env` occurring later in the string).
- **`touchesClaudeSettings()` (Section B) matched the raw, unresolved target path (found by Security Reviewer, confirmed via a real file overwrite on disk).** Unlike its siblings `touchesDataRoot()` and `touchesPluginInstallation()`, the Write/Edit/NotebookEdit arm never called `path.resolve()`, so `.claude/./settings.json`, `.claude//settings.json`, `.claude/x/../settings.json`, and an NTFS alternate-data-stream suffix (`.claude/settings.json::$DATA`, a distinct stream of the *same* file on Windows) all classified as `pass` and were independently confirmed to genuinely overwrite the real `settings.json`. Fixed by stripping a trailing `::<stream>` suffix, expanding a leading `~` the same way Bash command text already is elsewhere in this module, then resolving through `.`/`..`/double-separators before comparing the basename and immediate parent directory name -- the same resolve-then-compare shape the other two functions already used, which is exactly why review flagged the inconsistency.

**Independent review round 3 (fresh Verifier, fresh Reviewer, fresh Security Reviewer -- the org's API spend limit was hit mid-review twice in this checkpoint; each agent was resumed via message once the limit cleared, recovering their in-progress findings rather than losing the work) found that round 2 itself left real, reproduced gaps open -- including one Critical, product-breaking regression -- plus two further real bugs. All fixed:**

- **Critical -- `touchesPluginInstallation()`'s Bash/PowerShell arm denied KRYLO's own mandatory runtime CLI calls.** `skills/run/SKILL.md`'s own required calls are literally `node "${CLAUDE_PLUGIN_ROOT}/scripts/runtime/<script>.mjs"`; once that variable is expanded to a literal path (guaranteed for PowerShell, common for Bash), the Section B check introduced in this same checkpoint denied them outright, with no approval path -- breaking KRYLO's own operation after the first `init-run` call. Confirmed end to end through the real Hook process. Fixed by dropping the Bash/PowerShell arm entirely: the actual file-mutation threat is fully covered by the Write/Edit/NotebookEdit arm (unchanged) plus the pre-existing, narrowly-scoped `touchesHookEntrypoint()`, and command TEXT merely referencing `pluginRoot` is not, on its own, a reliable signal of anything -- as this bug itself demonstrated.
- **High -- the round-2 `rm` fix still evaded on the bare newline-joined form.** `git\nrm -rf /` (no `echo` prefix, no other separator at all) still classified as `pass`: after whitespace normalization collapsed the newline to a plain space, it read identically to the genuine single command `git rm -rf /`, which the exclusion correctly treats as benign. Fixed at the root cause, not by patching the lookbehind again: a newline is now normalized to an explicit `;` separator *before* other whitespace is collapsed, restoring the distinction every pattern in this file depends on (and incidentally re-activating each pattern's own long-dead `[^|;&\n]` exclusion, previously neutered by the same plain-space collapse).
- **High -- the round-2 git-push quoting fix still missed `git.exe push` and a quoted config value containing a space.** `\bgit\b` requires a word boundary immediately after "git", which `.exe` does not provide before reaching `push`; and `git -c user.name="A B" push` broke the option-token loop, since `user.name="A B"` is a single shell word (an unquoted prefix glued to a quoted segment) that the loop's simple quoted-or-plain alternation could not match as one unit. Both realistic, everyday forms. Fixed by allowing an optional `.exe`/`.cmd` suffix on `git`, and by matching an option value as a sequence of unquoted-or-quoted segments glued together, the same way a real shell treats it after quote-removal.
- **Medium -- the degraded (session-less) identity path omitted `pluginRoot` entirely**, silently disabling `touchesPluginInstallation()` (no signal at all, not even a safe default) for the exact scenario that path exists for -- an unresolvable session id whose active run is still found via the ADR-0020 fallback. The identical bug class already fixed once for `permission_mode` in `risk-gate.mjs`. Fixed by resolving `pluginRoot` in the degraded identity the same way the primary path does.
- **Medium -- quoted sensitive-path references bypassed secret-path protection entirely.** `cat ".env"`, `cat '.env'` (ordinary, everyday shell quoting), and a literally-quoted `file_path` value on Write/Read all classified as `pass`: the Bash token splitter and the Write/Read/Glob/Grep target checks never stripped surrounding quotes, so the sensitivePaths patterns' own path-boundary anchors (expecting a literal `.env` at the start, not a quote character) never matched. Fixed by stripping one matching pair of surrounding quotes before matching, everywhere a path-shaped value is checked.

**Independent review round 4 (a fresh Security Reviewer and a fresh Reviewer, dispatched in parallel against the round-3 commit specifically, since that commit was itself entirely reviewer-driven and Section J requires a fresh pass over whatever the final commit turns out to be) found that round 3 left one Critical, product-breaking regression, three further real High/Medium bugs, and one narrowing that itself reopened coverage round 1 had established. All fixed:**

- **Critical -- the round-3 line-normalization fix itself defeated nearly every require-approval class for any multi-line command.** Converting *every* bare newline to a command-separator (the round-3 fix for the bare-newline `rm` spoof) did not distinguish a real newline-as-separator from a Bash `\`-continuation or PowerShell backtick-continuation -- both of which are ONE logical command written across lines, not two commands. Every pattern in `production-policy.json` using a `[^|;&\n]*?`-shaped exclusion (production-deploy, destructive-operation, iam-or-secrets, release, merge, payment, external-write, git-force, and more) silently classified as `pass` for any of those continued into a second line. Reproduced for `kubectl \`+newline+`apply -f prod.yaml`, `terraform \`+newline+`destroy -auto-approve`, `aws iam \`+newline+`delete-user ...`, and PowerShell's backtick equivalent, among others -- a far larger availability gap than the narrow spoof the round-3 fix closed. Fixed by collapsing a `\`-newline or backtick-newline to a plain space FIRST, before any remaining bare newline is converted to a separator; the original bare-newline `rm`-spoof case (no continuation character) is unaffected and still gated.
- **Critical -- the redesigned git-push/git-force option-value pattern is an exponential-backtracking (ReDoS) regex.** `(?:\s+(?:-{1,2}[\w-]+(?:[=\s](?:[^\s"']+|"[^"]*"|'[^']*')+)?))*` nests one quantified alternative (`[^\s"']+`) inside another repeating group with no way to distinguish, on backtrack, how many characters each outer iteration consumed -- the textbook `(a+)+` shape. Measured: a 46-byte payload (`git -a="` + 26 unquoted characters + a trailing separator and unrelated command, deliberately with no closing quote and no `push` token so the overall match must fail) took ~1.9 seconds; each +2 characters roughly doubled that. Because `git-force`/`git-push` are checked early against every command, this is trivially reachable by a prompt-injected model and would hang the gate (a fail-open risk this module's own comments already flag for a genuine evaluation exception) well before the existing 10,000-character overall command-length guard is anywhere near relevant. Fixed by removing the redundant inner `+` (a single non-quantified character class inside the already-repeating outer group is sufficient to match the same set of shell words, without the ambiguity): confirmed by direct timing that the same adversarial shape now resolves in under 1ms up to a 1000-character payload.
- **High -- `matchesSensitivePath()` never stripped the NTFS alternate-data-stream suffix the round-1 `touchesClaudeSettings()` fix already handles.** `.env::$DATA` (a distinct stream of the same file on Windows) read straight through to real secret content while classifying as `pass`, on both Bash/PowerShell and Read/Write. Fixed by stripping a trailing `::<stream>` suffix inside `matchesSensitivePath()` itself, so every caller benefits without duplicating the logic.
- **High -- removing `touchesPluginInstallation()`'s Bash/PowerShell arm entirely (the round-3 fix for the Critical self-DoS) left the actual file-mutation threat unguarded for Bash/PowerShell.** `echo x >> <pluginRoot>/policies/production-policy.json`, `sed -i ... <pluginRoot>/scripts/security/risk-policy.mjs`, and the PowerShell equivalents (`Set-Content`/`Add-Content`/`Out-File`/`Copy-Item`/`Move-Item`/`New-Item -Value`) all mutate exactly the files this check exists to protect, and `touchesHookEntrypoint()` only covers six known hook-entrypoint filenames, not policy JSON or the run skill. Re-added a narrower Bash/PowerShell arm requiring BOTH a reference to `pluginRoot` AND a write-shaped signal (a redirection operator or one of the write-verbs above) -- a mandatory runtime CLI invocation (`node "<pluginRoot>/scripts/runtime/<script>.mjs" ...`) contains neither, so this does not repeat the round-3 self-inflicted regression; confirmed against all of `skills/run/SKILL.md`'s documented invocations plus a plain read (`cat`/`Get-Content`) still passing.
- **Medium -- a quoted path containing an internal space bypassed secret-path detection, and the round-3 quote-stripping fix for `touchesClaudeSettings()`/`touchesPluginInstallation()` did not extend to symlinked/junctioned parent directories.** `cat "my dir/.env"` split into two whitespace-delimited tokens (`"my` and `dir/.env"`) before quote-stripping ever ran, so neither fragment matched the path-anchored pattern; separately, a directory symlink/junction whose *name* is not literally `.claude` (or not under the resolved `pluginRoot`) passed the raw-path check while still landing on the real protected file once the OS resolved it -- the exact class of gap `touchesDataRoot()` already closed with `realpathBestEffort()`, which the round-1 fixes for the other two functions did not carry over (despite an earlier round's comment inaccurately claiming parity). Fixed: `commandTouchesSensitivePath()` now extracts whole shell words (a maximal run of ordinary characters and/or fully-quoted segments glued together, mirroring the git-push pattern's own "shell word" concept, with the same single-character-not-`+` construction so it cannot reintroduce the ReDoS above) before stripping quotes, so an internal space inside a quoted token survives as one token; `touchesClaudeSettings()` and `touchesPluginInstallation()`'s Write/Edit/NotebookEdit arms now also resolve through `realpathBestEffort()`, matching `touchesDataRoot()`.
- **Low -- a quoted absolute path to `git.exe` containing a space (e.g. `"C:/Program Files/Git/bin/git.exe" push`) still evaded the git-push pattern**, since the closing quote character sat between the `git`/`.exe` boundary and the required following whitespace. Fixed by allowing an optional matching quote character immediately after that boundary.

**Independent review round 5 (a fresh Security Reviewer, dispatched with an explicit mandate to judge whether the recurring pattern of "each round finds bugs in the last round's regex fixes" indicated a structural ceiling rather than isolated bugs) reached exactly that conclusion for one specific control, and found two further real bugs elsewhere. All addressed:**

- **Critical (by consequence) -- the round-4 `touchesPluginInstallation()` Bash/PowerShell write-shaped-signal design is negative-value: it is simultaneously a Critical false-positive generator AND covers only a small fraction of real write primitives.** Confirmed: the `>`/`>>` signal also matches `->`, `=>`, and `2>&1`/`1>file` inside ordinary, unrelated command text -- including KRYLO's own mandatory runtime CLI calls, whose JSON evidence payloads routinely contain such text (`--add-evidence '{"summary":"12 failing -> 0 failing"}'` was denied outright, with no approval path). Separately, of 16 real, distinct ways to mutate a file via Bash/PowerShell (`node -e`/`perl -pi`/`python -c` one-liners, `dd`, `truncate`, `install`, `rsync`, `ln -sf`, `curl -o`, `git checkout -- `, PowerShell `[System.IO.File]::WriteAllText`/`Remove-Item`/`Rename-Item`, and a flagless `rm <file>`), only 3 were caught by the fixed signal list -- confirming there is no finite verb list that closes this: every interpreter available on the box is its own write primitive, and a regex over untokenized shell text cannot answer "is this a write to file X" for an unbounded, interpreter-agnostic set of them. This is judged a genuine structural limit of the text-matching approach for THIS specific check (not a claim that regex-based classification is worthless generally -- the `approvalClasses` ask-routing and the sensitivePaths deny both remain sound, tokenized, path-anchored checks with a bounded, well-understood failure mode). Per the reviewer's explicit recommendation, the Bash/PowerShell arm is REMOVED rather than patched into a sixth round chasing the same failure mode: a control that blocks legitimate use while catching a small fraction of real risk is worse than no control, and pretending otherwise in SECURITY.md/this ADR would be a false guarantee. The Write/Edit/NotebookEdit arm (unchanged, genuinely tokenized and path-resolved) plus `touchesHookEntrypoint()` remain the actual protection; Bash/PowerShell-mediated mutation of the plugin's own installed files via an interpreter or another shell write primitive is now an explicitly disclosed, accepted residual gap for this specific tool surface (see the list below), not a closed guarantee that was ever safe to claim.
- **High -- the round-3 quote-stripping fix still left quote-CONCATENATION unhandled.** `cat .env""` and `cat "".env` (ordinary, valid shell syntax -- adjacent empty/partial quote pairs that a real shell still resolves to the literal file `.env`) still classified as `pass`, since stripping only one matching OUTER pair of quotes left an interior quote character in the token, which broke the path-boundary anchors just the same. Fixed by removing every quote character from a token, not merely a single surrounding pair -- verified this cannot re-lose the internal space the round-4 SHELL_WORD fix preserves inside a quoted segment, since a space is never a quote character.
- **High -- a trailing space or dot on a path component bypasses secret-path detection**, confirmed against a real PowerShell process (`Get-Content '.env '` reads the real `.env` -- Windows silently ignores a trailing space/dot on a path component). Fixed by stripping trailing spaces/dots inside `matchesSensitivePath()`, the same way the NTFS ADS suffix already is; confirmed this does not break the `.env.example` template exception (trimming a genuine trailing dot/space, not the filename's own final character).

Also confirmed by this round as correct and NOT reopened: the round-4 ReDoS fix (timed clean up to 20,000 adversarial characters), the continuation-collapse fix (Bash/PowerShell do not treat a continuation-with-trailing-whitespace, CRLF, or multiple consecutive continuations any differently, and correctly do NOT collapse a bare `\` or backtick not immediately followed by a newline), and the `realpathBestEffort()` wiring in both `touchesClaudeSettings()` and `touchesPluginInstallation()` (raw check first, realpath fallback second, consistently lowercased, no early-return bug).

**Independent review round 6 (a fresh Security Reviewer, dispatched against the literal final commit of round 5 specifically, per this task's own requirement that the final commit not go unreviewed) approved the revert and both secret-path fixes, with live reproduction, and found two further items -- one new Low false positive from the round-5 fix itself, one Medium pre-existing bypass not introduced by this checkpoint. Both fixed:**

- **Low -- the trailing-space/dot trim (round 5) masked ordinary free text ending in a real extension.** Confirmed: `git commit -m "regenerate cert.pem."` denied outright as `sensitive-path`, though it never referenced an actual path -- the extension-only patterns (`.pem`/`.key`/...), unlike the `.env`/`id_rsa` patterns, are not anchored to a path-start boundary, so trimming the trailing dot turned an unrelated sentence into something that matched. Fixed by scoping the trim: only applied when the FINAL path component, once trimmed, has no remaining internal space -- true for a genuine bare file reference or a real path whose filename segment has no space, false for a free-text sentence; confirmed this still correctly denies a real path with a space in an *earlier* segment and a genuine trailing dot (`cat "my dir/.env."`).
- **Medium, confirmed pre-existing (not introduced by this checkpoint) -- Bash ANSI-C (`$'...'`) and locale (`$"..."`) quoting bypassed secret-path detection**, confirmed against a real Bash process (`cat $'.env'` reads the real `.env`). The SHELL_WORD tokenizer glued the leading `$` into the token as ordinary text, so stripping only the quote characters left `$.env`, defeating the path-start anchor. This was already named in this ADR's residual-limitations list as a known gap rather than silently missed, but given it was reachable and independently reproduced, it is fixed rather than left disclosed: a `$` immediately before a quote character is now stripped along with the quote, since it is part of that quoting syntax, not path text.

**Also disclosed, accepted as residual limitations rather than fixed in this checkpoint (all Low unless noted, none a regression, all inherent to the same text-matching design already documented elsewhere in this module):**

- **(Elevated by round 5, not Low) `touchesPluginInstallation()` has NO Bash/PowerShell coverage at all**, by deliberate design after the round-4/round-5 history above: a model can mutate the plugin's own installed files (policy JSON, the run skill, non-hook-entrypoint scripts) via Bash/PowerShell using an interpreter one-liner or another shell write primitive, with no approval path and no denial. Round 6 independently confirmed the compensating controls that DO exist: a Bash/PowerShell edit of a hook-entrypoint file itself is still caught by `touchesHookEntrypoint()`, and a destructive delete of the whole `pluginRoot` directory is still caught by `destructive-operation`. This remains the one item in this list judged to materially matter for the Section K GO checklist; see the Foundation-status decision below for how this is weighed.

- `touchesClaudeSettings()`'s Bash/PowerShell arm remains a substring check with no read/write distinction (so even `cat .claude/settings.json` denies, not only a write), bypassable via ordinary shell indirection (`cd .claude && echo x > settings.json`, a variable holding the filename) -- the same category of limitation `touchesDataRoot()`/`touchesHookEntrypoint()` already document. The header comment and `SECURITY.md` are worded to state this explicitly rather than overclaim "only writes are gated... for any tool."
- ~~The D2 wildcard fix covers a literal trailing `*` but not every glob metacharacter...~~ **No longer accurate -- superseded by Section G below.** `.e*`, `.en?`, `.[e]nv`, `.*env`, bracket character classes, and the sensitive-extension family (`*.pem`, `*.[p]em`, ...) are now all recognized by a dedicated glob-aware matcher, not left as an accepted gap.
- The D1 `rm` fix does not recognize GNU long-form flags (`--recursive`, `--force`) or a target placed before the flags (`rm ./build -rf`) -- neither was covered before this checkpoint either.
- `stripSurroundingQuotes()` (round 5: removes every quote character in a token, not just an outer pair -- this now also correctly handles `.env''` and `.en"v"`, previously-disclosed cases that turned out to already be fixed by the same change; round 6: also strips a `$` immediately before a quote, closing the ANSI-C/locale-quoting bypass above) still cannot see through backtick/`$(...)` command substitution -- a genuinely complete shell-word parser is a materially larger undertaking than this checkpoint's text-matching design anywhere else attempts. `git pu''sh origin main` and a hyphenated `git-push` invocation remain unmatched by the git-push pattern for the same reason. `.env.example.` / `.env.example ` (a trailing dot/space appended to the template exception itself) are now also exempt -- correct on Windows (where they resolve to the same file), a distinct filename on POSIX, but not exploitable there since it does not resolve to a real secret.
- `touchesPluginInstallation()`'s protection depends on `pluginRoot` resolving to the actual *installed* plugin location, distinct from KRYLO's own source-repository checkout. When the host does not set its own plugin-root environment variable (real Claude Code sessions always do; an ad-hoc script invocation of this repository's own files might not), the host adapter's resolver falls back to a source-relative path -- which, when this module runs from within KRYLO's own repository, equals the repository checkout itself, and would then deny editing `plugins/krylo/**` there too. This is a real, disclosed precondition on the claim that this check "does not interfere with KRYLO-on-itself source development," not an unconditional guarantee independent of how the host resolves `pluginRoot`.

Except for the elevated item above (no Bash/PowerShell coverage for plugin-installation-protection, a genuine gap for that specific tool surface, weighed explicitly in the Foundation-status decision below), none of these residual items reverses a prior guarantee or reopens a previously-closed gap; they narrow an already-narrow, already-disclosed text-matching design further, or state an existing claim's real precondition precisely. Every item that WAS a genuine regression or a reachable, reproduced bypass (as opposed to a disclosed narrowing of an already-narrow design, or a control found to be net-negative and removed rather than kept) was fixed in this same checkpoint and is regression-tested.

### G. Glob-aware sensitive-path closure (Foundation glob-closure checkpoint, HEAD 76c9194)

A confirmed HIGH-severity gap, distinct from everything above: D2's fix (and every subsequent round's) recognized only a LITERAL secret filename/extension, never a filesystem glob expression that EXPANDS to that same name at shell/tool level -- `cat .e*` in a directory containing a real `.env` reads it identically to `cat .env`, but no sensitivePaths pattern requires or tolerates the literal text `.e*`. Confirmed real (not hypothetical) with an isolated shell fixture: a throwaway temp directory, a placeholder `.env` file, and a real Bash process demonstrating `.e*` expands to `.env` in that directory.

Per this task's explicit design requirement not to add one regex alternative per reported bypass, this is closed with a small, bounded, deterministic glob-matching primitive (`plugins/krylo/scripts/security/risk-policy.mjs`), not more regex:

- **Atom parsing.** A glob string (`*`, `?`, `[...]`/`[!...]` bracket classes, with bounded range expansion) is parsed into atoms in one linear pass -- consecutive `*` collapse to a single `star` atom.
- **Matching.** An atom sequence is matched against a literal target using the classic ITERATIVE two-pointer wildcard algorithm (the same shape as well-known bounded `fnmatch` implementations): O(atoms × literal length), no recursion, no exponential backtracking. The literal side is always one of KRYLO's own short, fixed canonical names (`.env`, `id_rsa`, `.pem`, ...), never attacker-controlled length, so this stays fast regardless of how long or complex the attacker's glob is.
- **Extensions** (`*.pem`, `*.key`, ...) are matched via a suffix search over candidate split points, walking backward from the end of the pattern. At the time this was bounded by a fixed `MAX_SUFFIX_SEARCH_ATOMS = 64` cap; **section H below replaces this with a provably-complete backward walk that needs no fixed bound at all** (a running count of non-star atoms consumed, which only grows as the search moves further back, proves every smaller split point is unmatchable once that count exceeds the target's own length).
- **Structured policy, not code, holds the canonical names**: `production-policy.json`'s `sensitivePaths` gained `globProtectedPaths` (exact/directory-scoped protected names, e.g. `.env`, `id_rsa`, `.ssh/*`) and `globProtectedExtensions` (`pem`, `key`, ...) -- the SAME lists a future protected name/extension is added to once, not duplicated across regex alternatives.
- **Wired into every required tool surface**: Bash/PowerShell (per shell token, not the whole multi-word command line -- see the over-blocking finding below for why), `Glob`'s `pattern`/`path`, `Grep`'s `glob`/`path` (never `pattern`, the content-search regex), `Read`'s `file_path`, and `Write`/`Edit`/`NotebookEdit`'s target.
- **Template exception preserved correctly**: a glob that can ALSO match `.env.example` (e.g. `.env*`) is still denied, since the exception only ever applies to an EXACT literal template name with no glob metacharacter present at all -- exactly the task's own required behavior (`.env.example` allowed, `.env*` denied even though it matches both).
- **Bash brace expansion**: a single, non-nested `{a,b,c}` group (bounded to 32 branches, 128 chars each) is expanded into its literal alternatives before the checks above, closing the narrow case the task asked to inspect without attempting a shell interpreter.

**A genuine over-blocking bug was found and fixed during this checkpoint's own test-first work, before it ever reached review**: a candidate glob made ENTIRELY of `*` (a bare `*`/`**`, no other content) trivially fully-matches ANY literal via the star atom's zero-or-more semantics -- without an explicit guard, `cat *`, `Glob(pattern: '**/*.js')`, and every other ordinary recursive/list-everything glob would have denied, exactly the "deny every command containing `*`" outcome this task explicitly prohibits. A second, related bug: running the glob check against the WHOLE multi-word Bash/PowerShell command line (not just each token) let an unrelated preceding word supply enough "discriminating content" for a trailing bare `*` to still slip through the extension-suffix search (`cat *` denied via matching `*.pem`-shaped extensions, since "cat *" as a whole string is not purely wildcard even though its meaningful final argument is). Both fixed: a candidate with no atom besides `star` is never treated as matching any specific name or extension, and the glob-aware check runs strictly per shell token, never the whole raw command line (the exact-match check keeps running against the whole line, unchanged, for its own pre-existing reasons).

`id_r?` (from the task's own listed examples) is a 5-character glob and cannot fully match any real 6-character protected key name (`id_rsa`, `id_dsa`) under correct, standard glob semantics (`?` matches exactly one character) -- verified as correct pass-through, not a residual gap: no real protected key name it could expand to exists. `id_rs?` (6 characters) does fully match `id_rsa` and is denied, confirming the matcher is exercising real glob semantics rather than a coincidental heuristic.

**A fresh independent Verifier, Reviewer, and Security Reviewer were then dispatched against this fix's own final commit. Verifier approved outright (with real mutation testing). Reviewer and Security Reviewer each found real, reproduced bugs in the fix itself -- one Critical, two High -- fixed in the same checkpoint before closing:**

- **Critical -- the extension-suffix search's discriminating-content guard was checked on the FULL pattern only, not each suffix slice the search loop actually tests.** `ls build*`, `cat README*`, `tar -czf out.tgz dist*`, and any other ordinary "prefix-then-star" command matched via the degenerate trailing-`*`-only slice inside the search loop (which by itself carries no discriminating content, even though the pattern as a whole plainly does) -- hard-denying routine wildcard commands with no approval path, the exact blanket-wildcard outcome this checkpoint's own task explicitly prohibits, just displaced from a bare `*` to `x*`. Fixed by checking `hasDiscriminatingContent()` against each SLICE tried in the loop, not merely the pattern as a whole; confirmed this does not lose the real positive (`build*.pem` still denies).
- **High -- a bare-wildcard FINAL segment under an already-confirmed protected directory was a real, reachable bypass.** `.aws/*`, `.kube/*`, and `.config/gh/*` all passed, since the bare-wildcard guard (correctly rejecting a context-free `cat *`) also rejected the filename position once every LEADING directory segment had already matched the specific protected name with real content -- reproduced reading the placeholder credential file in an isolated fixture. Fixed by allowing a bare-wildcard final segment to count ONLY for the trailing position of an already multi-segment-matched protected path (never for a non-final segment, and never for a single-segment protected name like `.env`/`id_rsa`, where the context-free over-blocking concern still fully applies).
- **High -- brace-only expansion (no other glob metacharacter) was unreachable.** The top-level gate checked for `*`/`?`/`[` but not `{`, so `.{env,x}` and `.en{v,w}` never even reached `expandSimpleBraceGroup()`, despite a real shell expanding braces unconditionally -- reproduced reading the fixture `.env` via `cat .{env,x}`. Fixed by adding `{` to that gate.
- **High -- a genuine ~19-second stall on Read/Write/Edit/NotebookEdit/Glob/Grep path fields**, none of which has Bash/PowerShell's `MAX_BASH_COMMAND_LENGTH` guard. A bracket-class body packed with hundreds of thousands of individually-bounded range specs (each already capped at 1024 codepoints) had no limit on how MANY such ranges one class could contain, driving total cost into the hundreds of millions of Set insertions for a real, reachable ~990,000-character candidate (well within the 1MB Hook-stdin size limit) -- measured at ~19 seconds before the fix, ~0.1 seconds after. Fixed at the time with `MAX_CLASS_SET_SIZE` (a total distinct-character budget per bracket class) plus a whole-candidate length cap for the glob-aware check specifically -- **the length cap was itself later found to be a fail-open bypass and removed; see the next review round below for the real fix.**
- A dead, unused policy field (`sensitivePaths.globTemplateExceptionSuffixes`, read by no code and inconsistent with the template-exception logic's real location in `matchesSensitivePath()`) was removed rather than wired in, per the Medium finding that flagged it.

Confirmed by the same review round as correct and NOT reopened: `globAtomsMatchLiteral` itself (differential-fuzz-tested against a brute-force recursive reference across 37,448 pattern/literal pairs with zero mismatches), the 64-atom suffix-search bound (provably sufficient at the time -- the longest protected extension needs at most 19 atoms; superseded by the unbounded provably-complete search in section H below), the multi-segment alignment logic, the brace-expansion bounds (branch count/length, no nesting), and the completeness of the port from the old regex list (all 12 original patterns represented in the new structured fields).

**A further independent Security Reviewer and Reviewer pair was then dispatched against THAT fix-of-the-fix commit specifically. All four fixes above were confirmed working correctly, but the same pass surfaced a worse version of the exact performance concern it had just closed, plus a real coverage gap in the brace-expansion fix. Both fixed:**

- **High -- brace expansion, stacked with the new length cap, multiplied into a 40-60 second stall, worse than the original ~19-second one.** The length cap was checked against the ORIGINAL text only, before expansion; each of up to `MAX_BRACE_BRANCHES` (32) expanded candidates could independently still be close to that same cap, and -- separately -- every candidate segment was being re-parsed from scratch once per `globProtectedPaths` entry PLUS once per protected extension (roughly 22 times per segment). Stacked together (32 candidates x 22 re-parses x a dense bracket-class body each), this drove total cost into the hundreds of millions of redundant operations. Measured at 40-60 seconds for a 4,094-character candidate combining a 32-branch brace group with a repeated bracket class -- reproduced identically on Read, Bash, and Grep. Fixed two ways: each candidate segment's atoms are now parsed exactly ONCE per candidate and reused across every subsequent check (removing the ~22x re-parse multiplier), and the length cap is checked again per EXPANDED candidate, not only the original text. Confirmed this brings the exact reported payload down to single-digit milliseconds.
- **High -- multi-group brace expansion only ever expanded the FIRST group.** `.e{n,m}{v,w}`, `{.,x}{env,y}`, and `.{e,f}{n,m}v` all still classified as `pass`, since the original single-pass expander left any SECOND group's literal `{`/`}` characters in the output untouched, even though a real shell expands every group in a word. Fixed with an iterative, fixed-point expander (bounded by `MAX_BRACE_GROUPS` rounds and a hard `MAX_TOTAL_BRACE_CANDIDATES` ceiling, so two or more groups cannot combine into a combinatorial explosion) that keeps expanding until no more in-bounds groups remain. At the time, a single group beyond `MAX_BRACE_BRANCHES`/`MAX_BRACE_BRANCH_LENGTH` was left as literal text -- **a later, dedicated review round (section H below) found this was itself fail-open, not a safe bound, and replaced it with a fail-safe `INDETERMINATE` result.**

**A further independent Reviewer was dispatched against that fix-of-the-fix commit. Three of its four fixes were confirmed correct; the fourth (the length cap added for the original stall) was itself a real, reachable bypass -- worse than a performance concern, since it disabled the check entirely rather than merely being slow. Fixed, along with one further real gap the same pass found:**

- **High -- the whole-candidate length cap was a fail-open bypass, not a bound.** Any candidate over the cap skipped the ENTIRE glob-aware check, exact-match check aside. Reproduced: `Read{file_path: './'.repeat(2100) + '.e*'}` (padded just past the cap with harmless leading segments) classified as `pass`, even though the real `.e*` danger was still present at the very end. This reopened every case this checkpoint exists to close, for anyone willing to pad their input. Root cause of the ORIGINAL stall was never the candidate's overall length -- only the TRAILING segments a protected path can possibly match against ever matter (at most 3, for `.config/gh/hosts.yml`) -- so the real fix removes the length cap entirely and instead only ever parses/examines the last `maxProtectedPathSegments` segments of any candidate, computed from the policy itself. Combined with a new `MAX_CLASS_ATOMS_PER_PATTERN` bound (capping how many bracket-class occurrences a single pattern is parsed for at all, directly targeting the actual cost driver rather than working around it via candidate length), the original 990,000-character stall now resolves in ~0.1s and the brace-plus-dense-class compounding stall in ~0.1-0.15s, with NO length-based bypass of any kind.
- **High -- a bare-wildcard segment was only relaxed at the FINAL position of a multi-segment protected path.** `cat .config/*/hosts.yml` (the MIDDLE segment wildcarded) and `cat */gh/hosts.yml` (the FIRST segment wildcarded) both still reached the real `.config/gh/hosts.yml` in a real shell but classified as `pass`. Fixed by allowing the relaxation at ANY ONE segment position rather than only the last. This reopens the SAME over-blocking risk the original relaxation was designed to avoid unless bounded carefully: at most one segment per protected-path check may use it (never two or more, which is what would let a fully generic `cat */*/*` match with zero real signal), and it is disabled entirely for a protected path that already carries its own policy-level `*` sentinel (`.ssh/*`) -- combining the sentinel's unconditional free pass with a second relaxed position would let `cat */*` match `.ssh/*` with nothing confirming either segment. Confirmed `cat */*/*`, `cat */*`, and `cat *` all still correctly pass, and `.ssh/config` (a genuine, non-generic reference) still correctly denies.
- Also corrected during this pass: a stale doc comment claiming the pre-existing exact-match check (`matchesSensitivePath()`) is "unaffected by cost, still runs regardless of length" -- true relative to this fix's own new bounds, but the same review measured that function's own regex-based matching scaling quadratically for a very large candidate (multiple seconds at tens of kilobytes). That scaling is pre-existing, present since before this checkpoint, and unrelated to anything in this diff; fixing it would be exactly the "reopen unrelated Foundation architecture" this checkpoint's own task explicitly prohibits. The comment and this document are corrected to state the true, narrower claim (unaffected by the NEW glob-specific bounds, not a general performance guarantee for arbitrary input) rather than overclaiming a property that was never actually tested.
- A missing assertion in the oversized-bracket-body performance test (it measured elapsed time but never asserted the resulting decision, so it would have silently accepted the length-cap bypass above as "fast enough") was fixed to also assert the correct `deny` outcome. A trivially-always-true condition in the bare-wildcard guard's plumbing (`atoms.length > 0`, checked against an already-non-empty segment) was simplified away during the same pass, along with removing an entire now-dead helper function the loop's inlined logic superseded.

**A final closing Security Reviewer was dispatched with an explicit request for a GO/NO-GO verdict, given the extensive review history already completed. It returned NO-GO: the five specific adversarial goals requested were not reproducible (no new padding bypass, no new bound defeat, no new relaxation-logic bypass, no reopened original stall), but adversarial probing surfaced one further real, in-scope bug, plus three genuinely pre-existing, out-of-scope findings. The in-scope bug is fixed; the others are disclosed per this task's own explicit instruction not to reopen unrelated Foundation architecture:**

- **High, in scope, fixed at the time (later closed properly -- see section H below) -- `secrets.json`/`secret.json`/`.yaml`/`.yml`/`.toml` denied `*.json`/`**/*.yml`/`*.toml` outright.** These four names share their entire identifying extension with an enormous, ordinary population of unrelated files (`package.json`, `tsconfig.json`, every YAML config, every TOML manifest); including them in `globProtectedPaths` let a leading star absorb the whole `secret(s)` stem while only the shared, generic extension matched literally, denying essentially all JSON/YAML/TOML wildcard operations repo-wide (lint, format, search) with no approval path -- confirmed via `ls *.json`, `Glob('**/*.json')`, `eslint **/*.yml`, `cat *.toml`, all wrongly `deny`. At the time, this was fixed by removing these four names from glob-aware matching entirely, leaving them only in the original exact-match `patterns` -- which reopened a straightforward bypass (`secret?.json`, `secrets*.yaml`, `[s]ecrets.toml` all passed uninspected). **This was accepted as a disclosed residual only until section H below, which closes it structurally without reintroducing the over-blocking regression.**
- **High, confirmed real, PRE-EXISTING, out of scope -- `realpathBestEffort()` (used by `touchesDataRoot()`/`touchesClaudeSettings()`/`touchesPluginInstallation()`, none of which this checkpoint touches) scales quadratically on a many-segment path with no glob metacharacter involved at all.** Measured: a 240KB path-shaped `Read`/`Write` field took ~193 seconds; extrapolated to the 1MB Hook-stdin cap, on the order of minutes. This is a real, separately-reachable availability concern, but it long predates this checkpoint, is reached by a completely different code path (symlink resolution for the data-root/settings/plugin-installation protections, not sensitive-path glob matching), and fixing it would be exactly the "reopen unrelated Foundation architecture" this checkpoint's own task explicitly prohibits. Disclosed here as follow-up work for a future, dedicated checkpoint, not fixed now.
- **Medium, PRE-EXISTING, out of scope -- `Grep(path: '.ssh')` (no trailing separator) is not caught by the exact-match `.ssh[\\/]` pattern.** No glob metacharacter is involved (so this never reaches any code this checkpoint added); a pre-existing gap in the original exact-match regex list, unrelated to the glob-closure feature. Disclosed, not fixed, for the same reason as above.
- **Medium, accepted design boundary, now explicitly disclosed -- `.config/*/*` (both the middle AND final segment wildcarded) is not denied against `.config/gh/hosts.yml`.** A direct, intentional consequence of the "at most one relaxed segment position" rule: allowing two relaxed positions here would be the same over-generalization the rule exists to prevent (as `cat */*` demonstrated against `.ssh/*` earlier in this same round). Not previously named explicitly in this residual list; added now.

Covered by 21 focused tests (`plugins/krylo/tests/unit/sensitive-path-glob.test.mjs`), including the real isolated-shell fixture, every form from the task's required-coverage list, PowerShell equivalents, Glob/Grep field-shape correctness, Write/Edit/NotebookEdit, path-traversal-plus-glob, the directory-scoped bare-wildcard case (final AND middle/first position), single- and multi-group brace expansion, the padding-bypass case, the shared-extension-vs-exact-literal case, and bounded-performance/adversarial-input cases (long star runs, long alternating metacharacters, a long bracket-class body, a genuinely matching worst-case shape, the oversized single-candidate stall, the brace-plus-dense-class compounding stall, and the padding-past-cap case) all resolving in double-digit milliseconds or faster. Full suite (342 tests) passes.

### H. Final bounded glob-closure: tri-state fail-safe redesign + generic-extension-basename structural fix (FINAL closure checkpoint)

A fresh external review of section G's own feature found a ROOT design flaw shared by every analysis bound introduced there: `MAX_BRACE_BRANCHES`, `MAX_BRACE_BRANCH_LENGTH`, `MAX_BRACE_GROUPS`, `MAX_TOTAL_BRACE_CANDIDATES`, `MAX_CLASS_SET_SIZE`, `MAX_CLASS_ATOMS_PER_PATTERN`, and `MAX_SUFFIX_SEARCH_ATOMS` each treated "budget exceeded" as either inert literal text or a silently-truncated result -- both of which resolve to a silent `pass` when the TRUE, unbounded analysis might have found a real match. Confirmed reachable, not hypothetical: a brace group with 33 branches including `env` (`.{env,z0,z1,...,z31}`) was intentionally classified `pass` because `MAX_BRACE_BRANCHES = 32`, even though a real Bash process expands that expression and includes `.env` -- `cat .{env,z0,...}` reaches the real secret while KRYLO passed it uninspected.

**Root fix: every glob-analysis function that can hit a resource bound was refactored around an explicit tri-state result -- `MATCH` / `NO_MATCH` / `INDETERMINATE`.** `isSensitivePath()`'s security rule: `MATCH` and `INDETERMINATE` both deny; only a confident `NO_MATCH` continues normal classification. An attacker-controlled complexity/budget limit can no longer turn into a `pass` anywhere in this module:

- `parseGlobAtoms()` now returns `{ atoms, indeterminate }`: exceeding `MAX_CLASS_ATOMS_PER_PATTERN` or `MAX_CLASS_SET_SIZE` (including a bracket-range expansion truncated by either the per-range 1024-codepoint cap or the class-wide budget) sets `indeterminate = true` rather than silently returning a partial atom list.
- `expandFirstBraceGroup()`/`expandSimpleBraceGroup()` now return `{ status: 'inert' | 'indeterminate' | 'expanded', candidates? }`. Exceeding `MAX_BRACE_BRANCHES`, `MAX_BRACE_BRANCH_LENGTH`, `MAX_BRACE_GROUPS`, or `MAX_TOTAL_BRACE_CANDIDATES`, or encountering nested braces (valid, expandable Bash syntax this module does not implement), now reports `indeterminate`. `inert` is reserved for constructs that are genuinely not brace syntax in any real shell either (no closing `}`, or a body with neither a comma nor a range operator) -- there, "no expansion occurs" is a fact about real shell behavior, not an analysis shortcut.
- **A brace RANGE (`{a..z}`, `{1..10}`, `{1..10..2}`) was found, during this checkpoint's own design work, to be an entirely unhandled fail-open gap not named in the task's own example list**: the original comma-splitting expander required at least 2 comma-separated branches, so a range body (no comma at all) silently fell through as "not valid brace syntax" and was treated as inert literal text, even though real Bash unconditionally expands it (`.{a..z}nv` genuinely expands to include `.env`, confirmed against a real Bash process). Fixed by detecting the range-operator shape (`/^[^,]*\.\.[^,]*$/`) and reporting `indeterminate` for it explicitly, rather than leaving it inert.
- `atomsMatchExtensionSuffix()` (the extension-suffix search) no longer needs `MAX_SUFFIX_SEARCH_ATOMS` at all: replaced with a provably-complete backward walk that tracks a running count of non-star atoms as the candidate split point moves backward -- since each non-star atom mandatorily consumes exactly one target character and the count only grows, once it exceeds the fixed target's own length every smaller split point is mathematically guaranteed unmatchable, and the search can stop with no information loss. No bound, no `INDETERMINATE` needed for this specific function.
- `globCouldTargetSensitivePath()` itself now returns one of `GLOB_MATCH` / `GLOB_NO_MATCH` / `GLOB_INDETERMINATE`: any candidate segment whose parse was flagged indeterminate, or whose brace expansion was indeterminate, denies -- even when no explicit `MATCH` was separately found elsewhere in the same candidate.

**Required RED-then-GREEN regression coverage** (`plugins/krylo/tests/unit/sensitive-path-glob.test.mjs`) demonstrates all of: a 33-branch brace group with one `.env`-yielding branch (`MAX_BRACE_BRANCHES`), a branch longer than `MAX_BRACE_BRANCH_LENGTH` alongside another `.env`-yielding branch, a brace-group count real Bash expansion confirms produces 32 real candidates (`MAX_BRACE_GROUPS`), a 125-candidate expansion (3 groups x 5 branches) confirmed by a real Bash process to include `.env` exactly once (`MAX_TOTAL_BRACE_CANDIDATES`), a bracket class whose decisive character sits past a 600-entry Private-Use-Area-padded budget (`MAX_CLASS_SET_SIZE`/`MAX_CLASS_ATOMS_PER_PATTERN` -- Private-Use-Area codepoints specifically chosen to avoid the case-folding collisions that undermined an earlier, discarded Greek-letter padding attempt), and the brace-range gap above -- every case now either positively recognizes the sensitive path or becomes `INDETERMINATE` and denies, each confirmed with a real isolated Bash fixture containing a placeholder `.env` (never a real secret or real user directory) where Bash was available. Benign small brace/glob commands (`cat notes.{txt,md}`, `ls *.txt`, `cat .[a-z]og.txt`, `cat build*`) are confirmed to still classify as `pass` -- the fail-safe redesign denies only genuine budget exhaustion, not ordinary bounded use. The one PRE-EXISTING test written under section G's now-superseded fail-open assumption (a 796-bracket-class payload combined with a 32-branch brace group, previously asserted `pass` because both bounds were "safely" exceeded) is updated to assert the new, correct `deny`/`indeterminate` outcome -- this is the intended, security-correct consequence of the redesign, not a regression.

**Second HIGH finding closed structurally: the secrets.json/secret.yaml generic-extension bypass.** Section G's fix for the shared-extension over-blocking problem (`*.json` denying outright) removed `secrets.json`/`secret.json`/`.yaml`/`.yml`/`.toml` from glob-aware matching entirely, which reopened a straightforward bypass: `secret?.json`, `secrets*.json`, `secr*.json`, `[s]ecret.json`, `[s]ecrets.toml`, `secret*.yaml`, `secrets?.yml`, and `config/secret?.yml` all passed uninspected, directly targeting filenames the exact-match `patterns` list already declares protected.

Closed structurally, per the task's explicit instruction not to hardcode one regex per example: `production-policy.json`'s `sensitivePaths` gains two new structured fields, `globProtectedGenericExtensionBasenames: ["secret", "secrets"]` and `globGenericExtensions: ["json", "yaml", "yml", "toml"]`, consumed by a new `atomsMatchGenericExtensionBasename()` in `risk-policy.mjs`. The algorithm answers the task's own framing directly -- "does this glob specifically constrain the basename enough that it can target the protected secret basename?" -- via a search symmetric to the extension-suffix search above: walk the split point between "basename" and "extension" forward from the start of the candidate's atoms (provably complete, same non-star-count argument as the suffix search, just walked in the opposite direction), and at each candidate split point require BOTH that the basename-side slice has genuine discriminating content and fully matches the protected basename literal (`secret` or `secrets`), AND that the remainder resolves to one of the protected generic extensions via the existing suffix search. A bare `*.json` has no discriminating basename content at all (only a star before the extension) and correctly passes; `package*.json`/`tsconfig*.json` have discriminating content but it does not match "secret"/"secrets" under real glob semantics and correctly pass; every required-deny example above specifically constrains its basename toward "secret"/"secrets" and correctly denies. Exact literal `secrets.json`/`secret.yaml`/`secret.toml` remain denied via the pre-existing, unchanged exact-match `patterns`. Confirmed via a dedicated regression test covering the full required must-deny/must-allow lists across Bash, PowerShell, Glob, and Grep, plus the full existing suite with no regression.

Full regression suite: 347 tests pass (up from 342 in section G, +5 net: the new generic-extension-basename test, the brace-range fail-open regression test, and the RED-then-GREEN analysis-bound coverage above, minus the one pre-existing test folded into the new bracket-class-budget coverage). `git diff --check`, `npm run syntax`, and `npm run validate:runtime` all pass clean on the resulting HEAD.

## Consequences

- Every require-approval class now has both a real human-approval path (ADR-0027) *and* live-verified evidence that a pre-existing allow rule cannot silently disable it (this ADR) -- the two together substantively answer KRYLO's product contract for the approval boundary.
- The model can no longer weaken Claude Code's own settings files (Write/Edit/NotebookEdit fully, Bash/PowerShell via a disclosed, imperfect substring check) via any of those tools -- closing a previously entirely-unaddressed gap.
- The model can no longer weaken the KRYLO plugin's own installed policy/hook/skill files via Write/Edit/NotebookEdit -- also closing a previously entirely-unaddressed gap. Two attempts to extend this to Bash/PowerShell were each found, by independent review, to be net-negative (a Critical false-positive generator covering only a small fraction of real write primitives) and were removed rather than kept; this specific tool surface for this specific new protection is a disclosed, accepted residual gap, not a claimed guarantee.
- Four real, previously-disclosed-but-unfixed classifier gaps (D1-D4) are fixed and regression-tested, along with roughly a dozen further regressions and bugs that FIVE consecutive rounds of independent review found in each prior round's own fixes -- every Critical/High finding across all five rounds is fixed and regression-tested; every Medium is either fixed or explicitly disclosed as non-blocking below.
- The mid-session dynamic "always allow" click and a live MCP variant remain not directly observed, disclosed rather than assumed; this is an accepted, reasoned gap given this checkpoint's environment constraints (no interactive human, no live write-capable MCP server), not an oversight.
- Section E (audit trail) is explicitly deferred with the task's own stated permission to do so.
- The stale-installed-plugin-cache discovery is recorded as important operational context for anyone relying on this development environment's "installed" KRYLO for further live testing; it does not affect the correctness of the source repository this checkpoint hardens.

### Foundation-status decision

The single item elevated above the routine residual-limitations list -- no Bash/PowerShell coverage for `touchesPluginInstallation()` -- is judged non-blocking for Foundation closure, for reasons distinct from every other disclosed residual in this ADR: it was investigated twice, not accepted on first difficulty; both attempted fixes were shown, with concrete reproduction, to make the security posture worse (one broke KRYLO's own operation, the other was net-negative coverage); and the underlying reason (no finite verb list can characterize "is this a write" for an interpreter-agnostic set of shell primitives) is a structural property of text-matching over untokenized shell text, not a fixable oversight in this codebase. It is also strictly additive relative to the pre-checkpoint baseline: `touchesPluginInstallation()` did not exist before this checkpoint, so its Write/Edit/NotebookEdit coverage (real, tokenized, path-resolved, symlink-aware) is new protection with a known, disclosed, and narrower-than-ideal boundary -- not a regression from a previously-stronger guarantee. Closing it properly requires a non-textual enforcement mechanism (filesystem permissions/ACLs on the installed plugin directory, or a content-hash integrity check of `policies/`+`scripts/security/` verified at each gate invocation) that is a materially different, larger design decision than a further regex patch, and is recorded as follow-up work rather than attempted under this checkpoint's remaining scope. On this basis, and given every other Foundation GO criterion in Section K is met with fresh, reproduced evidence -- including a round-6 Security Reviewer's explicit approval of the literal final commit, satisfying the requirement that the final commit not go unreviewed -- this checkpoint concludes GO FOR CODEX HOST with this one item named explicitly, not folded silently into routine disclosure.
