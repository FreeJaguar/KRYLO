# ADR-0034: Codex Runtime Compatibility Gate

## Status

Accepted

## Context

Every prior Codex checkpoint (ADR-0029, ADR-0032, ADR-0033) verified KRYLO's Codex hook contracts against either the locally installed `codex-cli 0.120.0` binary or, for `Stop`/`SessionStart`/`SessionEnd`, against the `rust-v0.152.1` release's own source (`codex-rs/hooks/...`) -- a 32-minor-version gap the capability matrix already discloses. Nothing in the shipped Codex host code ever checks, at run time, which of those two (or any other) version is actually installed on a given user's machine before letting `$krylo-run` bootstrap a full autonomous run. A user on a materially different Codex build -- older, newer, or a fork -- gets the exact same unconditional trust as the two versions KRYLO has actually reviewed.

### Re-verification against the current stable Codex release (not trusted from the prior checkpoint's own report)

Re-checked `gh api repos/openai/codex/releases` directly, fresh, in this checkpoint: **`rust-v0.152.1`** (published 2026-09-01) remains the current stable release; the next four most recent releases (`0.152.0`, `0.151.0`, `0.150.1`, `0.150.0`) are all older. No newer stable or non-prerelease tag exists. This is independent confirmation, not a reused claim.

### A concrete, previously undetected drift finding, discovered while researching this checkpoint

Direct byte-inspection of the actual installed `codex-cli 0.120.0` binary (`codex.exe`, resolved past its npm `.cmd` shim, its JS launcher, and the per-platform `@openai/codex-win32-x64` vendor package -- the same "resolve to the real executable identity" methodology `spawn-platform.mjs`/`detectCodexWorkerCapability` already use elsewhere) found its own embedded ASCII strings contain exactly `PreToolUse`, `PostToolUse`, `SessionStart`, `UserPromptSubmit`, `"Stop"` -- **not** `SessionEnd`, and not `PermissionRequest`. This independently reproduces (not merely repeats) ADR-0029's own original 5-event finding for this exact binary, and directly corroborates a result the pre-existing Ecosystem Maintenance checker (ADR-0031) already reports without any code change needed: `node plugins/krylo/scripts/maintenance/check-ecosystem.mjs --offline` currently reports `codex-hook-event-names-recognized: ATTENTION (severity high)`, `recommendedAction: "Verify unrecognized Codex Hook event(s) against the real installed binary's schema before trusting: SessionEnd"` -- because `plugins/krylo/hooks/codex-hooks.json` registers `SessionEnd` (ADR-0033, sourced only from `rust-v0.152.1` SOURCE inspection) while that checker's own known-accepted-event snapshot was never updated past the original 5-event list.

This is exactly the failure class this checkpoint exists to make structurally impossible to trust silently: a hook registration, or a lifecycle guarantee, whose evidence comes from a *different* Codex build than the one actually installed. It is disclosed here, and captured as reviewed evidence in the new compatibility contract (below), rather than fixed by editing `codex-hooks.json` or ADR-0033 -- reopening that ADR's own shipped registration is a separate, reviewable change outside this checkpoint's scope. **A structural limit worth stating plainly: if this installed binary's own hook-config parser is in fact strict about unrecognized event names (unverified either way in this environment, no authenticated session available), the Runtime Compatibility Gate built by this ADR cannot detect or prevent that specific failure mode, because the gate itself only runs *inside* a hook process -- if `codex-hooks.json` failed to load at all, no KRYLO hook, including this gate, would ever fire.** The gate's actual scope is narrower and is stated precisely in the Decision section.

### A second, real finding: `codex features list` is not a safe secondary probe

Evaluated as a candidate "safe local capability probe" (per this checkpoint's own hybrid-design requirement) before being rejected: `codex features list` failed outright in this exact environment --

```
Error: C:\Users\eliyahus\.codex\config.toml:3:16: unknown variant `default`, expected `fast` or `flex`
```

-- a failure caused entirely by this user's own local `config.toml`, unrelated to the installed binary's version or capabilities. A probe that can fail for reasons having nothing to do with compatibility is unsafe to treat as compatibility evidence: it would either falsely downgrade a genuinely compatible, reviewed binary, or (if ignored on failure) contribute nothing. `codex --version` was re-confirmed, by contrast, to be minimal, side-effect-free, and to have already been the sole probe basis for `scripts/host/cross-harness/codex-worker.mjs`'s own `detectCodexWorkerCapability()` (ADR-0030) with no reported reliability problem across this repository's own history. This checkpoint's hybrid design (below) therefore uses `codex --version` as its only live runtime probe, and treats "consider a second local probe" as evaluated-and-rejected, not silently skipped.

## Objective

Implement a local, deterministic Codex Runtime Compatibility Gate: before a full autonomous `$krylo-run` bootstraps on Codex, KRYLO determines whether the installed Codex runtime matches a locally reviewed compatibility contract, using only local evidence (no network access, no auto-update, no automatic trust of "latest"). This is admission control for a full autonomous run -- explicitly not an OS sandbox, updater, external vulnerability scanner, second policy engine, replacement for the Risk Gate, or permission to weaken ADR-0029's approval boundary or silently downgrade enforcement.

## Decision

### Hybrid design: reviewed contract metadata (primary) + a single bounded local probe (secondary)

- **Reviewed contract metadata**, `plugins/krylo/policies/codex-runtime-compatibility.json` -- a small, git-tracked, human-reviewed JSON document (the same convention as `policies/production-policy.json`/`policies/mcp-policy.json`), listing exact-version `supported` and `blocked` entries with the specific evidence and confirmed hook-event set each one earned. **No version ranges, no semver-compatible-range trust** -- an entry matches only by exact `major.minor.patch` equality, per this checkpoint's own explicit instruction not to trust a "compatible-looking" range without a proven-stable contract across it. Any version absent from both lists -- older or newer than anything reviewed -- is `unverified` by construction, never silently treated as compatible.
- **The single local runtime probe**: `codex --version`, resolved through the exact same portable, shim-aware executable resolution (`scripts/lib/spawn-platform.mjs`'s `platformSpawnTarget`) already proven for `detectCodexWorkerCapability()`, run with `shell:false`, a bounded 5-second timeout, and a small output-size cap. No other command is run. No network call is made. No model is invoked. No repository source or prompt content is ever sent anywhere by this probe.
- **New host-specific module** `plugins/krylo/scripts/host/codex/runtime-compat.mjs`: `loadCompatibilityContract()` (reads and schema-validates the JSON contract; a malformed file or unrecognized `contractSchemaVersion` is a `contract-malformed` result, never treated as "no restrictions"), `probeCodexVersion()` (the bounded `--version` probe, returns `{ok:false, reason}` for every missing/timeout/nonzero-exit/malformed-output case, never guesses), and `evaluateCodexRuntimeCompatibility()` (the orchestrator: probe first; on any probe failure, `status: 'probe-failed'`; on probe success, parse the version via the existing `parseCodexVersion()` (`scripts/lib/version-compare.mjs`, unchanged, reused not duplicated) and look it up in the contract -- exact match in `blocked` wins first (`status:'blocked'`), then exact match in `supported` (`status:'supported'`), otherwise `status:'unverified'`). Every non-`supported` status carries `trusted:false` and a precise, human-readable reason.
- **Testability without a real Codex binary**: `probeCodexVersion()` accepts an injectable `cliPath`/`env`, mirroring `detectCodexWorkerCapability()`'s own existing signature exactly (no new pattern invented). The Codex hook entrypoint itself resolves `cliPath` from `env.KRYLO_CODEX_CLI_PATH` (defaulting to `'codex'`) -- an operator/test-only override, never reachable through prompt content, following the same established convention as `KRYLO_STANDALONE_ROOT`. Tests use a small, deterministic, git-tracked fake-CLI fixture (mirroring `tests/fixtures/cross-harness/fake-worker.{sh,cmd,mjs}`'s own proven cross-platform-launch shape) rather than depending on a real Codex installation -- this repository's test suite must remain fully hermetic.
- **Integration point: `scripts/security/user-prompt-submit-codex.mjs`, and nowhere else.** This remains, unchanged in every other respect, the only place a KRYLO Codex run is ever created (ADR-0029's fourth-attempt architecture). Immediately after an explicit `$krylo-run` invocation is recognized and before any state is created, the gate runs once. On `trusted:true`, bootstrap proceeds exactly as before this ADR -- zero behavior change for a reviewed, supported runtime. On `trusted:false`, the run is still created (through the same `createInitialState`/`saveState` Shared Core functions, so a genuine, inspectable audit record exists -- "never silently do nothing") but is saved **already in a terminal state**: `terminalState: 'SAFE_BLOCKED'`, `phase: 'BLOCKED'`, with one `findings` entry (`severity:'high'`, `source:'codex-runtime-compat'`) carrying the precise compatibility reason. **No active-run pointer is ever written for this run** -- it was never active by any evaluation, so there is nothing to later clear, and `resolveActiveRun()`'s own existing `terminalState !== null` check means every other Codex hook (`risk-gate-codex.mjs`, `stop-gate-codex.mjs`, `session-start-codex.mjs`, `session-end-codex.mjs`) already treats it as inert with zero code change to any of them. The `additionalContext` response names the exact reason and the run id (inspectable later via `read-state.mjs --run <runId>` if desired), and explicitly instructs the model not to attempt the task autonomously -- converting what would otherwise be a silent, undetectable trust gap into an immediate, visible, precisely-explained one, the same philosophy ADR-0029's own third bootstrap attempt already established for a different capability gap.
- **Ordinary Codex sessions, and Codex sessions that never invoke `$krylo-run`, are completely unaffected.** The gate only ever runs after `parseInvocation()` has already confirmed an explicit `$krylo-run` first token -- identical to every other guarantee this hook already provides. No new hook event is registered; no change to `PreToolUse`/`Stop`/`SessionStart`/`SessionEnd`/`PostToolUse` wiring, timeouts, or fail-directions from ADR-0029/0032/0033.
- **No caching.** The probe re-runs on every explicit `$krylo-run` invocation. This checkpoint evaluated caching against its own explicit constraint ("avoid mutable trust caches unless there is a demonstrated need... never allow stale compatibility approval to authorize a different binary") and found no such need: `$krylo-run` invocations are rare (once per session, typically), the probe itself is a single bounded subprocess call, and a cache would need its own invalidation-on-binary-change logic this checkpoint has no evidence justifies the added complexity for.
- **Supply-chain binary identity**: the probe records the *resolved* executable path (via `platformSpawnTarget`, which already follows a Windows `.cmd`/`.ps1` shim to its real underlying target rather than trusting the bare command name) alongside the version, as audit evidence in the finding. A full-file content digest was evaluated and explicitly deferred, not silently omitted: the real installed binary in this environment is 183,800,112 bytes; hashing it fully took non-trivial, non-negligible time and would need to run on every `$krylo-run` invocation with no verified-good hash source to compare against locally (no network dependency is permitted for Core, per this checkpoint's own constraint) -- so it would add real cost for a value this checkpoint cannot currently redeem. A lighter-weight identity signal (e.g. a package-manager-recorded integrity value, not explored this checkpoint) is left as a disclosed follow-up, not a claimed capability.
- **A second local capability probe (raw binary string-scan, or `codex features list`) was evaluated and explicitly rejected**, per the two findings above: the binary scan is portable and fast enough on this exact machine (431ms for a full 183MB read) but adds real, size-dependent latency with no bounded worst case across arbitrary future binary sizes/disks, and `codex features list` is demonstrably unreliable for reasons unrelated to compatibility. `codex --version` alone is the hybrid design's full local-probe layer for this checkpoint; a future checkpoint may add a bounded, capped secondary probe with its own review if a concrete need arises.

## Failure semantics (all fail toward `trusted:false`, never toward "compatible")

Every one of the following resolves to a precise, distinct `status` value, all of which the bootstrap hook treats identically (create the run, then immediately `SAFE_BLOCKED`, never "proceed anyway"): Codex missing (`probe-failed`), malformed `--version` output (`probe-failed`), a version that is not in either contract list (`unverified`), an exact-match `blocked` entry (`blocked`), probe timeout (`probe-failed`), an unexpected process error/exception (`probe-failed`), a malformed compatibility registry file (`contract-malformed`), and an unrecognized `contractSchemaVersion` (`contract-malformed`). No path in `runtime-compat.mjs` converts a probe error into `trusted:true`; there is no code path capable of doing so, by construction, matching this codebase's established "no code path capable of X" pattern (ADR-0029's own `emitCodexPreToolAsk` non-existence) rather than a runtime check that could be bypassed by a future edit.

## Security boundary

Compatibility evidence is code/runtime evidence only. The gate never reads `payload.prompt` (or any other model-influenced hook field) to decide `trusted`; the model has no code path to assert, claim, or influence a compatibility verdict, and no such claim -- were the model to make one in its own output text -- is ever parsed or trusted by this module. Both new files live under `pluginRoot` (`plugins/krylo/policies/codex-runtime-compatibility.json` and `plugins/krylo/scripts/host/codex/runtime-compat.mjs`), so both are already covered by `risk-policy.mjs`'s existing `touchesPluginInstallation()` Write/Edit/NotebookEdit/apply_patch protection with zero new code -- the same reviewed-policy-file protection `production-policy.json`/`mcp-policy.json` already have, now proven with an explicit regression test naming both new files. `runtime-compat.mjs` is deliberately **not** added to `HOOK_ENTRYPOINT_FILENAMES`: unlike every entry already on that list, it has no side-effecting `main()` of its own and consumes no stdin -- it is a pure library of exported functions, imported by `user-prompt-submit-codex.mjs`. Directly running `node runtime-compat.mjs` with fabricated input does nothing at all (no exported function is invoked at module load), so there is no forgeable state mutation for that list to prevent here; adding it anyway would misstate what the list actually protects against for every other entry on it.

## Consequences

- A reviewed, `supported` Codex runtime (currently: `0.120.0` exactly) bootstraps `$krylo-run` with zero behavior change from before this ADR.
- Any other installed Codex version -- including the current upstream stable, `0.152.1`, which KRYLO has only ever verified via source inspection, never by actually running it -- now gets an explicit, precise `SAFE_BLOCKED` run and a clear explanation instead of unconditional trust. This is a deliberate narrowing of default trust, not a regression: nothing about `0.152.1`'s ACTUAL runtime behavior was ever locally proven before this checkpoint either; this ADR makes that fact visible instead of implicit.
- The confirmed capability gap this checkpoint's own research surfaced (`SessionEnd` unconfirmed against the installed binary's own strings) is recorded as reviewed evidence in the new contract file, not silently fixed -- reopening `codex-hooks.json`'s registration is out of this checkpoint's scope and is disclosed as a follow-up.
- Adding a new supported (or blocked) version is a deliberate, reviewed, human-made edit to `plugins/krylo/policies/codex-runtime-compatibility.json` plus this ADR (or a superseding one) -- never automatic, never CI-driven, never a side effect of an unrelated commit, mirroring ADR-0022's Claude Code version-upgrade policy exactly.
