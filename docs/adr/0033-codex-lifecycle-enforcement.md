# ADR-0033: Codex lifecycle enforcement (Stop, SessionStart, SessionEnd)

## Status

Accepted

## Context

`docs/codex-capability-matrix.md` disclosed three Codex lifecycle events as deliberately deferred: `Stop` ("the exact Codex `Stop` hook output schema was not confirmed against primary docs during this checkpoint's research pass; shipping an unverified schema for budget enforcement was judged higher-risk than deferring it"), `SessionStart`, and `SessionEnd` (both "Not implemented this checkpoint... Documented follow-up"). This ADR closes those three specifically -- `SubagentStart`/`SubagentStop`/`PreCompact`/`PostCompact` remain out of scope, since current released-runtime evidence does not prove any of them is strictly required for these three.

Without `Stop`, KRYLO's Codex host has no Codex-side enforcement of the Orbit budget/completion contract at all: a Codex `$krylo-run` session can be ended by the model or user at any point, with no deterministic mechanism forcing continuation while unmet criteria and remaining budget exist -- the exact guarantee `scripts/orbit/stop-gate.mjs` already provides on the Claude host.

### Re-verification against the current stable Codex release

Re-checked `gh api repos/openai/codex/releases`: **`rust-v0.152.1`** remains the current stable release (unchanged since ADR-0032; `0.153.0-alpha.*` remains a pre-release). All findings below are from direct inspection of that exact tag's source, not `main`, not documentation alone.

**`Stop`** (`codex-rs/hooks/src/events/stop.rs`, `codex-rs/hooks/schema/generated/stop.command.{input,output}.schema.json`):

- Input (all required): `session_id`, `turn_id`, `cwd`, `model`, `permission_mode`, `stop_hook_active` (boolean), `last_assistant_message` (nullable), `transcript_path` (nullable). `stop_hook_active` is Codex's own recursion guard, structurally identical to Claude's field of the same name -- Codex's own comment history and the `crate::engine::ClaudeHooksEngine` type name confirm the hook wire protocol is a deliberate compatible reimplementation of Claude's, not an independent design.
- Output: `{"decision":"block","reason":"..."}` is the **only** supported blocking shape (`BlockDecisionWire` enum has exactly one value, `"block"`). Directly confirmed accepted, not merely schema-valid, by the handler's own unit tests run against the real parser: `block_decision_with_reason_sets_continuation_prompt` proves `{"decision":"block","reason":"..."}` sets `should_block: true` and injects the reason as a continuation prompt fragment -- functionally identical to Claude's own `{decision:'block', reason}` contract `scripts/host/claude/hook-transport.mjs`'s `emitClaudeStopBlock()` already emits.
- **Critical safety property, directly confirmed by the handler's own tests, not assumed:** every malformed/invalid/incomplete Stop output resolves to **`should_block: false`** -- i.e. fails toward LETTING THE SESSION END, never toward blocking it. `block_decision_without_reason_is_invalid` (`{"decision":"block"}` with no `reason`) fails and does not block. `invalid_stdout_fails_instead_of_silently_nooping` (non-JSON stdout) fails and does not block. This is the opposite fail-direction from `PreToolUse` (where invalid output fails OPEN toward allowing the tool call, the dangerous direction there) -- for `Stop`, failing toward "let it end" is the SAFE direction: a script bug can at worst let a session end early, never trap it in an unstoppable loop. This is the specific, verified, deterministic guarantee the task requires before `Stop` may ever emit a blocking decision.
- `continue_false_overrides_block_decision`: an output containing both `continue:false` and `decision:"block"` resolves to `should_stop: true` -- `continue:false` wins. KRYLO's Codex Stop gate therefore never emits a `continue` field at all when blocking (its absence defaults to `true` per the output schema, letting `decision:"block"` take effect cleanly).
- No documented or observed hard limit on repeated Stop-hook blocking beyond `stop_hook_active` itself and whatever budget the hook script's own logic enforces -- exactly the situation on Claude, where `scripts/orbit/stop-gate.mjs` is what bounds it (Orbit budget + stagnation), not the platform. KRYLO's Codex Stop gate reuses that exact same Shared Core logic unchanged, so the same bound applies identically.
- No explicit Stop timeout cap found in source (unlike `SessionEnd`, below); this ADR keeps the same generous 60-second budget the Claude Stop hook already uses (`skills/run/SKILL.md`'s existing `Stop` registration).

**`SessionStart`** (`codex-rs/hooks/src/events/session_start.rs`, schema files):

- Input (all required): `session_id`, `cwd`, `model`, `permission_mode`, `source` (`startup|resume|clear|compact`), `transcript_path` (nullable). No `turn_id` -- fires before any turn exists.
- Output: `hookSpecificOutput: {hookEventName:'SessionStart', additionalContext}` -- informational only, cannot block, cannot create state on Codex's own side. `source` is also usable as the hook's own matcher input, but this ADR registers with no matcher (fires for every source) since no source-specific behavior is required.
- No mechanism exists, or is used, to create a run from this event -- `additionalContext` is advisory text for the model, nothing more.

**`SessionEnd`** (`codex-rs/hooks/src/events/session_end.rs`, `session-end.command.input.schema.json`):

- Input (all required): `session_id`, `cwd`, `reason` (schema `const "other"` -- the **only** value this build ever reports; Codex does not yet distinguish a crash from a normal exit from `/clear` at the hook-input level), `transcript_path` (nullable). No `turn_id` in the schema despite the struct carrying one internally for hook-run bookkeeping only.
- **No output schema exists for this event at all** (`session-end.command.output.schema.json` returns 404; `parse_completed` in the Rust source produces `data: ()`, the unit type). SessionEnd cannot return any decision, cannot block anything, and its output is never parsed for content -- confirmed structurally, not inferred.
- **Directly confirmed timeout constraint, from source constants, not guessed:** `SESSION_END_DEFAULT_TIMEOUT_SEC = 1`, `SESSION_END_MAX_TIMEOUT_SEC = 3`, with the source's own comment: "SessionEnd runs during teardown and must leave headroom within the existing five-second bound." A SessionEnd handler that performs anything beyond a fast, single state read/write risks being killed mid-execution by the platform's own teardown budget.
- SessionEnd runs during **graceful** teardown. Nothing in this source, or in current official docs, claims it fires on an abrupt crash, `kill -9`, or forced process termination -- this ADR does not claim that guarantee, and the implementation must not either.

Fetched `https://learn.chatgpt.com/docs/hooks` again to re-confirm no newer guidance narrows or contradicts the source-level findings above; none found.

Evidence categories used below match `docs/codex-capability-matrix.md`'s existing convention: **locally passed**, **statically inspected**, **configured but not run**, **blocked by platform**.

## Decision

- **Stop is implemented, reusing Shared Core unchanged.** New `scripts/orbit/stop-gate-codex.mjs` mirrors `scripts/orbit/stop-gate.mjs` structurally: same `resolveActiveRun`, same `completionEval`, same `assessStagnation`, same Orbit-budget check, same `finalize()`-shaped terminal persistence, same file-lock-scoped decide-then-mutate sequence. Zero Orbit/completion/budget/stagnation policy is reimplemented in the Codex adapter -- only the Hook payload parsing and output shaping differ, per ADR-0023's architectural rule. New `emitCodexStopBlock(reason)` in `scripts/host/codex/hook-transport.mjs` emits exactly `{"decision":"block","reason":reason}` -- no `continue` field, ever, per the confirmed `continue_false_overrides_block_decision` precedence. Every path that is not "an active, non-terminal, budget-and-stagnation-permitting run bound to this exact session" emits nothing (silent allow, matching the fail-toward-ending-the-session safe direction confirmed above): no active run, wrong/mismatched session, malformed payload, `stop_hook_active` already true (Codex's own recursion guard, checked first, mirroring `stop-gate.mjs`'s identical Claude-side check), a run already in ANY terminal state (`state.terminalState !== null`, the single field shared by all six terminal states -- `VERIFIED_COMPLETE`, `SAFE_BLOCKED`, `USER_DECISION_REQUIRED`, `RISK_APPROVAL_REQUIRED`, `ITERATION_LIMIT_REACHED`, `CANCELLED_BY_USER` -- so no per-state special-casing is needed or added), budget exhaustion, or stagnation.
- **SessionStart is implemented as a narrow, non-activating informational hook.** New `scripts/security/session-start-codex.mjs`. It never creates a run, never sets `KRYLO_HOST`/data-root state beyond a normal read, and never emits `additionalContext` unless an active, non-terminal KRYLO run is ALREADY bound to this exact `session_id` and project (e.g. a resumed session) -- in that one case it emits a short, factual reminder ("a KRYLO run is already active for this session; continue it") through `hookSpecificOutput.additionalContext`, never a fabricated "KRYLO is active" claim when nothing is. `$krylo-run` via `UserPromptSubmit` (`scripts/security/user-prompt-submit-codex.mjs`, unchanged) remains the only place a run is ever created -- this ADR adds no second bootstrap path.
- **SessionEnd is implemented as a minimal, fast, best-effort evidence marker.** New `scripts/status/session-end-codex.mjs`. Given the confirmed ~1-3 second platform budget, it performs at most one already-validated state read (via `resolveActiveRun()`, which internally gates on `terminalState !== null`) and, only when an active NON-terminal run is bound to this exact session+project, one `recordEvent()` telemetry write noting the session ended while the run was still active -- it never mutates `terminalState`, never deletes evidence, never calls the bulk `scripts/runtime/cleanup.mjs` retention sweep (wrong scope entirely -- that utility is sessionless and operates across every run in the data root, not "the exact bound run" this ADR requires). It deliberately takes **no lock**: a review round found and live-reproduced that SessionEnd's own ~1-3s platform kill window is shorter than `scripts/lib/lock.mjs`'s up-to-6s retry budget (which has no staleness/PID recovery), so a killed SessionEnd holding that lock could orphan it and degrade every later locked caller for the same run. `recordEvent()` is an independent, already-atomic `fs.appendFileSync`, so no lock was ever needed for correctness here. An already-terminal run, a missing run, or a malformed session identity all resolve to a pure no-op. This is never claimed as a crash-recovery mechanism: SessionEnd runs during graceful teardown only, and an abrupt termination may simply never fire it -- the design does not depend on it firing for correctness, only records it as a nicety when it does.
- **Project-hook and plugin-hook parity.** All three new handlers are registered in both `plugins/krylo/hooks/codex-hooks.json` (plugin-bundled) and, via `install-codex.mjs --target hooks`'s existing `EVENT_LAUNCHER_ARG`/`EVENT_SCRIPTS` tables (`docs/adr/0032`), the project-scoped launcher (`codex/project-hooks/codex-project-hook-launcher.mjs`) -- the exact same real scripts, never a second implementation. `Stop`'s project-hook launcher path fails toward the SAME safe direction confirmed above (silent allow) if the real runtime cannot be located, matching `PreToolUse`'s existing fail-closed reasoning inverted for this event's own safe direction; `SessionStart`/`SessionEnd` no-op silently on a missing runtime, matching the existing `UserPromptSubmit`/`PostToolUse` convention.
- **Hook-entrypoint tamper protection extended.** `risk-policy.mjs`'s `HOOK_ENTRYPOINT_FILENAMES` gains `stop-gate-codex.mjs`, `session-start-codex.mjs`, `session-end-codex.mjs` -- without these, a model could directly invoke any of the three with fabricated stdin (e.g. forging a `Stop` payload with a crafted `session_id` to probe for another session's run, or bypassing the Orbit budget check by never letting the real hook fire).
- **No change to `require-approval` semantics, ADR-0029's approval boundary, or ADR-0032's write-protection scope** (`.codex/hooks.json`, the ownership sidecar, and `.codex/krylo/` remain protected; the three new launcher-invoked filenames are covered by the SAME existing `touchesCodexProjectHooks()`/`touchesHookEntrypoint()` checks, which key off the whole `.codex/krylo/` directory and the entrypoint-filename list respectively, not per-file enumeration).

## Consequences

- Codex now has genuine, verified, deterministic Orbit-budget enforcement at the Stop boundary, closing the last capability-matrix-disclosed gap in KRYLO's Codex-vs-Claude lifecycle parity for the three events in scope.
- The `Stop` gate's safe-fail-toward-ending-the-session property means a KRYLO Codex run can, in a genuine hook/runtime malfunction, end earlier than Orbit would otherwise have permitted -- treated as an acceptable, disclosed trade-off (never the reverse: an unstoppable loop).
- SessionEnd's guarantee is explicitly weaker than "cleanup always happens" -- documented as best-effort, graceful-teardown-only, consistent with what the released runtime itself proves and no more.
- Live, authenticated confirmation that Codex actually fires these three hooks for a real session (including the exact teardown timing for `SessionEnd`) remains unexercised in this environment -- recorded as environment-blocked in the capability matrix, not claimed as verified.

## Supersedes

None. Closes the `Stop`/`SessionStart`/`SessionEnd` rows `docs/codex-capability-matrix.md` already disclosed as deferred. Does not modify ADR-0021 (Claude-only), ADR-0029's approval boundary, or ADR-0032's project-hook ownership/merge design.
