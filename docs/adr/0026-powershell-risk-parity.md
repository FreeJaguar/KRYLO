# ADR-0026: PowerShell risk-classification parity with Bash

## Status

Accepted

## Context

KRYLO supports Windows (`docs/process/...`, `README.md`), where Claude Code frequently invokes shell commands through a distinct **PowerShell** tool rather than Bash. Before this checkpoint, `scripts/security/risk-policy.mjs`'s `classifyRiskAction()` branched explicitly on `toolName === 'Bash'` for every command-string check: the oversized-command cap, data-root protection, Hook-entrypoint protection, sensitive-path detection, and the production/destructive/publish/release policy classes in `policies/production-policy.json`. A PowerShell tool call fell through every one of these checks untouched and was classified `{ action: 'pass' }` regardless of what it did — the exact same `git push`, `Remove-Item -Recurse -Force`, or attempt to read `.env` that Bash would have gated was invisible to KRYLO when invoked through PowerShell instead. `skills/run/SKILL.md`'s risk-gate Hook matcher (`"Bash|Write|Edit|NotebookEdit|mcp__.*"`) did not even list PowerShell, so the Hook was never invoked for it at all.

Official Claude Code Hook documentation (`code.claude.com/docs/en/hooks`, checked for this task) confirms PowerShell is a distinct tool name from Bash, documents `"matcher": "Bash|PowerShell"` as the pattern for covering both, and — checked directly against a PowerShell Hook example in the same documentation (`$callInput.tool_input.command`) — confirms `tool_input.command` is the same field name PowerShell uses to carry the actual command text, exactly like Bash.

A separate, real gap was found in `policies/production-policy.json`'s `destructive-operation` class: its only destructive-delete pattern was the Bash-flavored `\brm\s+(-[a-z]*[rf][a-z]*\s+)+(/|~|\$HOME|[a-z]:\\)`, which does not match the PowerShell-native equivalent a real PowerShell user or a PowerShell-invoking model would actually write, `Remove-Item -Recurse -Force <path>`. An initial fix added only the single, fully-spelled `\bremove-item\b[^|;&\n]*?-(recurse|force)\b` pattern; independent security review then empirically demonstrated (by calling `classifyRiskAction()` directly) that PowerShell's own parameter-prefix matching and its built-in command aliases trivially evaded it: `Remove-Item -Rec -Fo`, `Remove-Item -R -F`, `ri -Recurse -Force`, `rd /s /q`, `rmdir -Recurse -Force`, `del /f /s /q`, and `rm -Recurse -Force .` (a relative path, which the pre-existing Bash pattern's own absolute-path requirement also misses) all classified as a silent `pass`.

## Decision

- `classifyRiskAction()`'s oversized-command cap, `touchesDataRoot()`, `touchesHookEntrypoint()`, and the Bash/PowerShell command-classification branch (sensitive-path check, `firstMatchingClass()` against `production-policy.json`) all now match on `toolName === 'Bash' || toolName === 'PowerShell'`, reading `tool_input.command` identically for both.
- `policies/production-policy.json`'s `destructive-operation` class pattern is `\b(remove-item|ri|rd|rmdir|del|erase)\b[^|;&\n]*?(-r\w*|-f\w*|/s\b|/q\b|/f\b)`, covering `Remove-Item` and its `ri`/`rd`/`rmdir`/`del`/`erase` built-in aliases together with PowerShell's parameter-prefix abbreviations (`-r`/`-rec`/`-recurse`, `-f`/`-fo`/`-force`) and the legacy `cmd.exe`-style `/s`/`/q`/`/f` flags `rd`/`rmdir`/`del` also accept. This is a heuristic, not an exhaustive parser of PowerShell's parameter-binding rules; it is deliberately permissive (a false positive here means an unnecessary `require-approval`, never a silent bypass). **`rm` is deliberately excluded from this alias list**, even though it is also a valid PowerShell alias for `Remove-Item`: an earlier version of this fix included it, and because the alternation has no path/target anchor, it turned ordinary Bash hygiene commands with no PowerShell involvement at all (`rm -rf node_modules`, `rm -f package-lock.json`, `docker rm -f <container>`, `git rm -r --cached .`) into unconditional denies with no in-run unlock. The accepted residual is narrow: PowerShell's `rm` alias with a *relative* path target only (e.g. `rm -Recurse -Force .`) is not caught by this pattern; a drive-letter, `/`, or `~`-rooted target (e.g. `rm -Recurse -Force C:\`) still is, via the pre-existing, separately-anchored Bash `rm` pattern in the same class.
- `skills/run/SKILL.md`'s risk-gate `PreToolUse` matcher becomes `"Bash|PowerShell|Write|Edit|NotebookEdit|mcp__.*"`.
- Risk **classification** (`pass`/`deny`/`require-approval` and `actionClass`) is now identical for Bash and PowerShell for every pattern in `production-policy.json`, `touchesDataRoot()`, `touchesHookEntrypoint()`, and sensitive-path detection. This is proven by regression tests, not an unconditional guarantee: like every text-pattern-matching defense in this file (`touchesDataRoot()`'s own documented limitation), a sufficiently obfuscated command — indirection through another interpreter, string concatenation/variable expansion the classifier does not evaluate, an alias not in the list above — is not caught by design, on either tool, equally.
- Risk **gating outcome** is not identical, and this is a deliberate, separate decision (see ADR-0025): a Bash `git-push`/`git-force` `require-approval` classification (only, per ADR-0025's narrowing) becomes Claude Code's native `permissionDecision: "ask"`; every other require-approval classification on PowerShell (indeed, on any tool) becomes a deterministic `deny`, because the official documentation that justifies trusting `ask` is explicitly scoped to Bash and was not found to extend to PowerShell anywhere in the CHANGELOG through the current released version. `deny` is strictly more conservative than an unconfirmed `ask`, never a weaker gate — a risky PowerShell action is still fully caught, just not resolvable through a live human prompt within the same run. On a Windows host where Claude Code uses PowerShell as its primary or only shell tool (no Git Bash installed), this means every gated class has no in-run resolution path at all for that tool — a real platform consequence, not merely a hypothetical one, disclosed in ADR-0025's Consequences and in SECURITY.md.

## Consequences

- Regression coverage added at both layers: `tests/unit/risk-policy.test.mjs` (direct `classifyRiskAction()` calls for PowerShell push, force-push, native destructive delete and its aliases/abbreviations, sensitive-path read, Hook-entrypoint invocation, data-root reference, oversized command, and a benign pass) and `tests/hooks/risk-gate.test.mjs`/`tests/governance/hook-scoping.test.mjs` (the real Hook process and the Skill frontmatter matcher).
- `tests/hooks/risk-gate.test.mjs`'s data-root/sensitive-path/hook-entrypoint PowerShell coverage confirms the outright-`deny` categories are completely unaffected by this ADR-0025-driven ask/deny split — those were never candidates for `ask` in the first place (they are not `require-approval` classifications).
- If official Claude Code documentation later confirms the same auto-mode-`ask`-flooring guarantee for PowerShell, `risk-gate.mjs`'s tool-name/action-class check should be extended (and this ADR superseded) rather than silently widened without an equivalent evidence trail.
