# ADR-0029: Codex host packaging and approval boundary

## Status

Accepted

## Context

ADR-0023 approved Claude Code and Codex as equal first-class KRYLO hosts and promised that "Codex receives its own explicit host invocation in a later ADR." `docs/process/MULTI_HOST_CODEX_MAINTENANCE_DESIGN.md` (2026-08-20) is the approved architecture for that work; `docs/process/CODEX_HOST_IMPLEMENTATION_PLAN.md` (this checkpoint) reconciles that design against current official Codex documentation, re-verified 2026-08-26, and records several refinements the original design could not have known in advance:

- Codex Skill implicit-invocation control lives in a separate `agents/openai.yaml` file (`policy.allow_implicit_invocation: false`), not SKILL.md frontmatter.
- PreToolUse's `permissionDecision: "ask"` (and legacy `decision: "approve"`, `continue: false`, `stopReason`, `suppressOutput`) are confirmed unsupported and fail the hook if returned.
- PermissionRequest only fires when Codex's own state was already about to prompt; it cannot manufacture a prompt for an action that would otherwise proceed without asking.
- Codex project/user rules (`prefix_rule` in a Starlark `.rules` file) match shell command **prefixes** only -- they have no mechanism to gate `apply_patch` or an MCP tool call.
- The Codex IDE extension (VS Code) does not support plugins at all; only the ChatGPT desktop app and Codex CLI's plugin browser do.

These facts materially constrain how KRYLO's `require-approval` classification can be honored on Codex and were not fully resolved in the original design's Section 9.3, which described a Core-level `GateDecision` shape but left the exact per-class mapping to implementation.

## Decision

- **Packaging.** KRYLO ships a real Codex CLI plugin at `plugins/krylo/.codex-plugin/plugin.json`, reusing the existing `plugins/krylo/` Core source tree (no second copy of Core), with an explicit `krylo-run` Skill (`skills/krylo-run/SKILL.md` plus `skills/krylo-run/agents/openai.yaml` setting `allow_implicit_invocation: false`) and plugin-bundled hooks registered at an explicit, Codex-only path (`hooks/codex-hooks.json`, referenced directly by the manifest's own `hooks` field) rather than the shared `hooks/hooks.json` Codex would otherwise auto-discover by convention -- the same directory convention Claude's (deliberately empty, ADR-0021) plugin-wide hooks file already relies on for its own "an ordinary Claude session launches zero KRYLO hook processes" guarantee.
- **HostContext.** A Codex adapter (`scripts/host/codex/context.mjs`, `scripts/host/codex/hook-transport.mjs`) mirrors the existing Claude adapter pattern exactly: it is the only code allowed to read Codex-specific environment variables (`PLUGIN_ROOT`, `PLUGIN_DATA`, the `CLAUDE_PLUGIN_*` compatibility aliases) and hook payload fields (`session_id`, `turn_id`, `cwd`, `permission_mode`, `model`), normalizing them into the existing host-neutral `HostIdentity`/`HostContext` contract (`scripts/lib/host-context.mjs`). Shared Core (`risk-policy.mjs`, `state.mjs`, Orbit, completion, approvals) is not modified beyond what Codex's own tool-name normalization genuinely requires, and any such change preserves the Claude regression suite unmodified.
- **PreToolUse never emits an unsupported field.** The Codex PreToolUse gate (`scripts/security/risk-gate-codex.mjs`) translates a KRYLO `pass`/`deny` decision directly into the confirmed-supported `permissionDecision: "deny"` (or silent pass) shape. It has no code path capable of emitting `"ask"` or any of the other four confirmed-unsupported fields -- there is no `emitCodexPreToolAsk` function in the codebase, by construction, not by convention.
- **`require-approval` approval boundary (security-critical, the central decision of this ADR).** Current official Codex documentation does not state the execution order between project/user rules, PreToolUse hooks, and the base `approval_policy` -- specifically, whether a rule's own native prompt fires before or after PreToolUse, and whether a PreToolUse hook that returns no decision implicitly skips or preserves downstream rule/approval evaluation is undocumented. Because this ordering is unverified, KRYLO's PreToolUse gate does not attempt to detect "this specific command is covered by an installed rule" and trust that coverage:
  1. **Every** `require-approval` classification -- shell, `apply_patch`, or MCP -- **fails closed** at PreToolUse: KRYLO denies deterministically, with a reason naming the specific capability gap and directing the user to perform the action outside the autonomous run or under an explicitly supported Codex approval path. This is preferred over any form of faked approval parity (auto-allow, a KRYLO-local approval record treated as authority, silently downgrading `require-approval` to `pass`, or trusting an unverified hook/rule execution order for a security decision).
  2. Rule provisioning (Task 6 of the implementation plan) remains a genuinely useful, **independent** capability: an operator may install a KRYLO-generated `prefix_rule(decision="prompt")` for a small, deterministic shell-command set so that Codex's own native approval flow can prompt for that exact command shape at the operator's discretion, entirely outside a KRYLO autonomous run (i.e. for ordinary, non-KRYLO Codex sessions in the same project). It is documented in the capability matrix as exactly that -- an independent Codex-native safety net, not a mechanism KRYLO's own gate trusts or depends on -- until a real, isolated smoke test empirically confirms a specific, safe interaction KRYLO's gate could rely on. If a future checkpoint verifies that ordering and finds a safe way to let a rule-covered, user-approved action proceed without weakening this boundary, that is a deliberate, reviewed change to this ADR, not an assumption baked in now.
  3. `PermissionRequest` is used only as defense in depth (denying a KRYLO hard-deny action if Codex was already about to prompt for it) and never as a mechanism to create an approval event KRYLO itself did not classify as `require-approval` and never to auto-approve one.
- **Hard-deny remains hard-deny** regardless of `permission_mode` (`bypassPermissions`, `dontAsk`, or any other/unknown value) -- identical guarantee to the Claude host.
- **VS Code.** Because the IDE extension does not support plugins, full VS Code KRYLO support uses a standalone user-level Skill plus explicit project-scoped `<repo>/.codex/hooks.json` setup (dry-run, ownership metadata, backup, explicit approval, rollback), per the design doc's Section 10. A standalone Skill without a trusted project hook layer runs read-only diagnostics rather than silently operating as a full autonomous run with a missing enforcement layer.
- **Rules are transport, not a second policy source.** Generated `.rules` files exist only to route specific shell-command-shaped `require-approval` classes to Codex's native prompt; they duplicate no classification logic (`production-policy.json` remains the single source of truth for which classes require approval at all) and provision no `forbidden` rule, since KRYLO's own PreToolUse hard-deny already covers that case without a second, harder-to-review enforcement location.

## Consequences

- KRYLO's `require-approval` guarantee is **narrower on Codex than on Claude for every class**: Claude routes every `require-approval` class through native `ask` (ADR-0027); Codex denies every `require-approval` class deterministically instead, since no verified in-hook mechanism exists today to reliably produce (and wait on) the same real human decision. This is a documented, capability-driven asymmetry, not an oversight, and is recorded in the Codex capability matrix. A KRYLO Codex run therefore cannot perform a `require-approval`-classified action autonomously at all; the operator must act outside the run (or, for the shell-command subset, may separately rely on an installed rule for an ordinary, non-KRYLO Codex session).
- Every unsupported Codex capability (forced PreToolUse ask, hosted-tool hook visibility, plugin support in the IDE extension) has an explicit safe fallback (fail closed, or "documented residual, not a security guarantee") rather than a silent gap.
- Codex-specific code stays limited to packaging, HostContext extraction, tool/input normalization, lifecycle event translation, permission/rule transport, capability detection, and setup/install integration, per the design doc's own architectural rule (Section 5.2): if a future change requires Codex to reimplement risk classification, approval rules, completion rules, Orbit decisions, evidence semantics, or tool trust policy independently of Shared Core, that is a design failure requiring its own review, not a routine implementation choice.
- Cross-Harness advisory workers, the weekly Upstream Watch, the monthly Ecosystem Radar, and the 0.2.0 version bump remain out of scope for this ADR and are not authorized by it.

## Independent review finding, fixed before closure

A fresh independent Verifier, dispatched against this ADR's own implementation commit, found the "hard-deny remains hard-deny... identical guarantee to the Claude host" claim above was **false for `apply_patch`** as first shipped: `classifyRiskAction()` (Shared Core, unchanged by this ADR's own diff) had no case for the `apply_patch` tool name at all, so it silently fell through to the function's unconditional final `pass` -- the same fallback used for a genuinely unrecognized tool. Reproduced live: an `apply_patch` call updating or creating `.env` with real-looking secret content both classified as `pass`, with zero protection, on a tool surface `production-policy.json`'s Write/Edit/NotebookEdit equivalent already hard-denies.

Fixed in the same checkpoint, before closure: `classifyRiskAction()` now extracts every target path from `apply_patch`'s own `patch` text (`*** Add File:`/`*** Update File:`/`*** Delete File:`/`*** Move to:` headers -- a single call can touch multiple files) and runs each one through the same data-root, hook-entrypoint, plugin-installation, and sensitive-path checks Write/Edit/NotebookEdit already receive. A patch with zero extractable targets (malformed, unrecognized shape, or a deliberate evasion attempt) fails safe -- deny, consistent with this module's own fail-safe philosophy elsewhere (docs/adr/0028's tri-state glob redesign) -- never a silent pass just because parsing found nothing. Regression-tested (`risk-gate-codex.test.mjs`): sensitive-path, data-root, plugin-installation, rename-into-sensitive-path, unparseable-patch, and benign-file cases, 52/52 passing.

This closes the gap the "identical guarantee to the Claude host" claim above already asserted; no wording change to that claim was needed once it was made true.

## Second independent review round: hook wiring corrected against the real installed binary's own schema

A second review round (independent Verifier, Reviewer, and Security Reviewer, dispatched against the commit containing the `apply_patch` fix above) found the Codex hook *wiring* itself did not match the platform this checkpoint's own plan claimed to verify against. Two facts were independently confirmed by direct byte inspection of the installed `codex-cli 0.120.0` binary (`codex.exe`, not merely documentation, and independently re-verified a second time after an initial verification attempt failed due to a broken search tool in the sandbox, not an absence of evidence):

- The binary's own embedded PreToolUse JSON Schema constrains `tool_name` to the literal **const `"Bash"`** for every command-hook invocation (`"tool_name": {"const": "Bash", "type": "string"}`, found verbatim at two locations in the binary alongside the full `PreToolUseToolInput`/`HookEventNameWire` schema). `hooks/codex-hooks.json`'s original matcher (`"shell|exec_command|apply_patch|mcp__.*"`) never matches the literal string `"Bash"` under any regex semantics -- meaning the PreToolUse hook, and therefore the entire Codex `require-approval`/hard-deny boundary, **never fired at all** on the exact build this checkpoint verified `codex execpolicy check` and `codex --version` against.
- `"PermissionRequest"` is **absent** from the binary's own embedded `HookEventNameWire` enum (confirmed value: `["PreToolUse", "PostToolUse", "SessionStart", "UserPromptSubmit", "Stop"]`). Registering an event name the installed build's own hook-config parser does not recognize risked the entire `hooks/codex-hooks.json` file failing to load, which -- had strict parsing been in effect -- would have silently dropped the working `PreToolUse`/`PostToolUse` registrations along with it.

Fixed before closure: `hooks/codex-hooks.json`'s matcher now includes the literal `"Bash"` first (keeping the other alternatives as forward-compatible matches for a future/differentiated build, per currently published docs describing broader tool-name coverage that may not yet have shipped in this exact npm package version); the `"PermissionRequest"` registration is removed entirely (the underlying `permission-request-codex.mjs` script remains implemented, ready to wire back in once a build confirmed to support the event is verified). `risk-gate-codex.test.mjs`'s own payload fixtures were corrected to use the real, confirmed `tool_name: "Bash"` shape rather than a documentation-sourced `"shell"` guess. A new governance test (`hook-scoping.test.mjs`) asserts the matcher includes `"Bash"` and that no unconfirmed hook event is ever registered.

This is recorded as a concrete instance of the exact failure mode this ADR's own security posture depends on avoiding: documentation (including this checkpoint's own "CURRENT PLATFORM FACTS" reconciliation pass) can describe a newer or different Codex build's behavior than what is actually installed, and only direct verification against the real, running artifact -- not the published docs alone -- can be trusted for a security-critical wiring decision. Live, authenticated confirmation that the corrected matcher actually causes the hook to fire on a real Codex session remains unexercised in this environment (no authenticated Codex account credentials were used) and is recorded as such in the capability matrix, not claimed as verified.

## Session-id bootstrapping: three attempts, and why the third is a disclosed capability gap rather than a working fix

A real, independent problem, separate from the matcher/event fixes above: current Codex documentation does not expose the real session identifier to the MODEL anywhere -- only to Hook payloads (confirmed open upstream gap, `openai/codex#8923`). This module's own `main()` requires a `--session` argument, and every hook resolves the run's active-session match strictly (`scripts/lib/hook-utils.mjs`'s `resolveActiveRun`) -- so whatever session id the model passes to `init-run.mjs` must equal the real one every later hook observes, or KRYLO's own enforcement silently disables itself for the entire run.

**Attempt 1 (in the original implementation commit): the model invents a placeholder session id.** An independent Reviewer reproduced the failure directly: a model-invented id never matches the real `session_id` a real hook payload carries, so `resolveActiveRun()` returns inactive for the whole run and every Codex hook silently no-ops -- total, undetectable loss of enforcement, the worst possible failure mode for a security control.

**Attempt 2: this hook rewrites a fixed literal placeholder (`KRYLO_CODEX_SESSION`) to the real session id via PreToolUse's `permissionDecision:"allow"` + `updatedInput`.** Confirmed schema-valid at the time (the binary's own JSON Schema declares both fields). Fixed the Skill's instructions to use the placeholder; added `emitCodexPreToolAllowWithRewrite()`; added regression tests. A THIRD independent review round then found, by direct byte inspection of the same installed binary's own hook-output validation error-string table (the same table this ADR already relies on for the `ask` rejection), that `permissionDecision:"allow"` and `updatedInput` are BOTH explicitly rejected on this build too: `"PreToolUse hook returned unsupported permissionDecision:allow"` and `"...unsupported updatedInput"` sit in that table immediately adjacent to `"...unsupported permissionDecision:ask"`. Being schema-valid (parseable) is not the same as being accepted by the actual handler -- the exact distinction this ADR's own `ask` analysis already draws, recurring in a second, easy-to-miss place. Independently re-confirmed via the same byte-search method used throughout this ADR's own verification history, not merely trusted from the review report.

**Attempt 3 (current, shipped): deny a placeholder-bearing command outright, loudly.** `emitCodexPreToolAllowWithRewrite()` and the rewrite mechanism are removed entirely (an "allow"-shaped emitter this build rejects has no safe use). `risk-gate-codex.mjs` now checks, before the active-run gate (so it also covers the bootstrapping `init-run.mjs` call itself), whether a Bash command contains the literal placeholder text, and denies it with a reason explaining the disclosed platform limitation. This converts an undetectable silent failure into an immediate, visible one on the very first command of any Codex run -- but it means **automatic KRYLO run bootstrapping does not currently work end to end on the verified-installed Codex build**. `skills/krylo-run/SKILL.md` documents this explicitly: the model is instructed to check for a real, directly-observable session identifier (in case a future/different build exposes one some other way), and if none is available -- the confirmed current default -- to stop before ever calling `init-run.mjs` and report the limitation rather than attempt a run with broken session binding.

This is recorded in `docs/codex-capability-matrix.md` as a confirmed, disclosed capability gap, not a working feature. Closing it properly requires either an upstream Codex capability (resolution of `openai/codex#8923`, or confirmation that a `SessionStart` hook's `additionalContext` output -- present in the schema, absent from the same rejection table, but not live-tested here -- reliably surfaces the real session id to the model) or a different, not-yet-designed bridging mechanism verified against a real, authenticated Codex session. Until then, the Codex host's security/classification logic (PreToolUse deny, hard-deny, `apply_patch` coverage, the matcher fix above) is real and tested; the ability to *start* a fully autonomous, enforced Codex run through `$krylo-run` alone is not.

## Correction: the three-attempt analysis above was solving the wrong problem, not an unsolvable one

**The "no safe session identity bridge exists on Codex 0.120.0" conclusion above is superseded and was incorrect.** All three prior attempts shared one unexamined premise: that the model itself would have to obtain, carry, or assert the session id (invented, rewritten via `PreToolUse`, or checked for and refused). That premise is what made the problem unsolvable -- `openai/codex#8923` confirms only that the *model* cannot introspect its own session id, never that no *hook* can. It was never necessary for the model to know the session id at all.

Reverified directly against the official `rust-v0.120.0` source tag (`gh api repos/openai/codex/contents/<path>?ref=rust-v0.120.0`, not memory, not summarized documentation), confirming every field below is genuinely present and genuinely accepted by this exact build, not merely a newer/different build's documentation:

- `UserPromptSubmit`'s own input schema (`codex-rs/hooks/schema/generated/user-prompt-submit.command.input.schema.json`) carries `session_id`, `turn_id`, `cwd`, `model`, `permission_mode`, and `prompt` as **required** fields -- the authoritative identity, delivered directly by the host, before the model ever produces a single token of that turn.
- `UserPromptSubmit`'s own output schema and event-handler source (`codex-rs/hooks/src/events/user_prompt_submit.rs`) confirm `hookSpecificOutput.additionalContext` is genuinely accepted for this event -- unlike `PreToolUse`, where the same field name sits in the confirmed-rejected table above. The two events do not share an output contract; the earlier attempts' failures do not generalize to this one.

**Fourth attempt (current, shipped): host-authoritative bootstrap at `UserPromptSubmit`, closing the gap.** `scripts/security/user-prompt-submit-codex.mjs` is now the *only* place a KRYLO Codex run is ever created. It fires on every Codex prompt (Codex has no Skill-scoped hook lifecycle), stays inert (silent exit, no state touched) unless the prompt's first non-whitespace token is exactly `$krylo-run` with a real token boundary, and on a genuine explicit invocation binds the new run directly to `payload.session_id` -- never a model-supplied argument, never `process.env.CODEX_THREAD_ID` alone (confirmed by `codex-rs/core/src/exec_env.rs` to be an injected shell environment variable, visible to and potentially influenced by the command surface; usable only as a non-authoritative diagnostic/consistency check, never a root of trust). It reuses Shared Core's own `createInitialState`/`saveState`/`writeActiveRunPointer`/`readActiveRunPointer`/`loadState` (`scripts/lib/state.mjs`) directly -- the same functions `runtime/init-run.mjs` itself calls -- so no run-initialization logic is duplicated. `risk-gate-codex.mjs` (`PreToolUse`) now plays no role in session bootstrap at all: it only resolves the already-active run via the real `session_id` on its own, separate hook payload, exactly as `risk-gate.mjs` (Claude) always has.

This removes every mechanism the three attempts above introduced: the placeholder-invention path, `emitCodexPreToolAllowWithRewrite()` and the `permissionDecision:"allow"`+`updatedInput` rewrite it depended on, and the placeholder-deny fail-safe built to contain attempt 2's failure. None of those were ever the model's responsibility to work around in the first place; the fix was to stop asking the model to participate in identity at all.

`docs/codex-capability-matrix.md`'s "Session-id binding -- CONFIRMED, UNRESOLVED CAPABILITY GAP" row is corrected accordingly (see that file). Automatic KRYLO run *creation* on Codex is implemented and fixture-verified against the verified schema and process-level fixture tests (`tests/hooks/user-prompt-submit-codex.test.mjs`); only a live, authenticated Codex smoke test remains unexercised in this environment, and is recorded as environment-blocked, not as a platform limitation.

## Fourth review round: a fresh Reviewer and Security Reviewer both independently reproduced a cross-session CLI collision, plus a missing hook-entrypoint-protection gap

Dispatched independently against the commit implementing the correction above, a fresh Reviewer and a fresh Security Reviewer -- working from the diff alone, with no access to each other's findings -- both traced and reproduced the same real bug, and the Security Reviewer separately found and reproduced a second one.

**Finding A (HIGH, independently confirmed twice): session-less CLI calls silently resolved to the wrong Codex session's run.** The rewritten `skills/krylo-run/SKILL.md` instructs the model to omit `--session` on every `read-state.mjs`/`update-state.mjs` call, exactly mirroring how the Claude Skill already does -- correct on Claude, because `resolveClaudeSessionId()` falls back to a real `CLAUDE_SESSION_ID` environment variable. `resolveCodexSessionId()` had no equivalent fallback at all (a deliberate choice at the time, since current Codex docs do not document a standalone session-id environment variable the way Claude's `CLAUDE_SESSION_ID` is documented). With no explicit `--session` and no hook payload, `hostSessionId` resolved to `undefined`, and `readActiveRunPointer()` fell through to its own documented ADR-0020 "most recently updated pointer for this host+project" fallback -- across *every* session, not just the caller's own. Both reviewers reproduced this directly: two Codex sessions bootstrapped in the same project, then a session-less CLI call from session A landed on session B's run instead, mutating its criteria/evidence/phase/terminal-state.

This is exactly the cross-session isolation guarantee this checkpoint's own design exists to establish, broken one layer up from where the hook itself was already correctly isolating sessions (both reviewers separately confirmed the *hook's* own session binding was clean; the bug was purely in the later, session-less CLI resolution path).

Fixed: `resolveCodexSessionId()` (`scripts/host/codex/context.mjs`) now falls back to `env.CODEX_THREAD_ID` -- the platform-injected shell-execution environment variable this ADR's own earlier verification pass already confirmed (`codex-rs/core/src/exec_env.rs`) carries the same underlying `ThreadId` as `session_id` -- mirroring `resolveClaudeSessionId()`'s existing `env.CLAUDE_SESSION_ID` fallback exactly, at the same trust level, for the same purpose: resolving which *already-created* run a later CLI call targets, never creating or binding a run's identity (that remains exclusively `user-prompt-submit-codex.mjs`'s job, using only `payload.session_id`, unaffected by this fix). This is squarely the "convenience for non-security-sensitive helper behavior" this ADR's own Decision section already reserves for `CODEX_THREAD_ID`, extended from "unused" to "used, but only as a lookup key with no bearing on run creation." Regression-tested end to end: two sessions bootstrapped in the same project, a session-less call with `CODEX_THREAD_ID` set to session A's id, asserting the criterion lands on A's run and B's run stays completely untouched (`tests/hooks/user-prompt-submit-codex.test.mjs`).

**Finding B (MEDIUM, Security Reviewer, reproduced): the four new Codex hook entrypoints were uncovered by `risk-policy.mjs`'s hook-entrypoint-protection list.** That list (`HOOK_ENTRYPOINT_FILENAMES`) denies a model's own Bash/PowerShell command from directly invoking a KRYLO Hook script with fabricated stdin -- but it listed only the Claude-era filenames, and a Codex filename is never a substring of its Claude counterpart (`"risk-gate-codex.mjs"` does not contain `"risk-gate.mjs"`). The Security Reviewer reproduced a concrete exploit: with a run already halted at `RISK_APPROVAL_REQUIRED`, directly piping a forged payload into `user-prompt-submit-codex.mjs` created a *fresh* run with a full, un-consumed Orbit budget, silently overwriting the halted run's active pointer -- resurrecting past a halt that existed specifically to force human review, with no real Codex event or user prompt involved. Bounded impact (no permission escalation: `createInitialState` still hardcodes conservative `lane`/`risk` defaults, and `classifyRiskAction` does not consult run state), but a real autonomy-limit bypass. Fixed: `user-prompt-submit-codex.mjs`, `risk-gate-codex.mjs`, `permission-request-codex.mjs`, and `posttool-telemetry-codex.mjs` were added to `HOOK_ENTRYPOINT_FILENAMES`. Regression-tested (`tests/unit/risk-policy.test.mjs`): all four now deny direct invocation.

Both fixes were verified against the full regression suite (`npm test`, 443+ passing) before this ADR was updated to reflect them.

One further, low-severity note from the same round: `hook-transport.mjs`'s `normalizeCodexHookPayload()` degraded-identity path (used when a PreToolUse-shaped payload lacks a usable `session_id`) now binds directly to `CODEX_THREAD_ID` instead of falling through to `hostSessionId: undefined`, whenever that variable happens to be present in the Hook process's own environment -- an improvement if so, but whether Codex actually sets `CODEX_THREAD_ID` in a Hook's own spawned process (as opposed to the model's own later shell execution environment, which `codex-rs/core/src/exec_env.rs` does confirm) is unverified and untested; treat this path as unverified, not regressed.
