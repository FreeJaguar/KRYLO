# KRYLO Claude Host Capability Matrix

- Checkpoint: `docs/adr/0030-cross-harness-advisory-workers.md`, `docs/process/CROSS_HARNESS_IMPLEMENTATION_PLAN.md`
- Installed Claude CLI verified against: `2.1.197 (Claude Code)`, real authenticated session (`claude auth status`: `loggedIn: true`, `authMethod: claude.ai`, `subscriptionType: team`)
- Scope: this is the first Claude-side capability matrix this product has needed -- Claude host capabilities before Cross-Harness were documented inline in ADRs (0025/0027) rather than in a dedicated matrix. It currently covers only the capabilities Cross-Harness introduced (invoking `claude -p` as an opposite-provider advisory worker); it is not a restatement of the whole Claude host.
- Evidence categories, matching `docs/codex-capability-matrix.md`'s own convention: **locally passed** (real command executed, real output observed), **statically inspected** (source/config read and reasoned about, not executed), **blocked by platform** (this environment cannot exercise it).

| Windows executable resolution (`spawnSync('claude', ...)`) | **Confirmed broken on the naive approach; the FIRST fix attempt was itself confirmed exploitable and has been replaced; the current mechanism is fixed and locally passed** | Direct reproduction: `spawnSync('claude', [...], {shell:false})` fails with `EINVAL` on this platform (npm-installed CLIs are `.cmd` shims on Windows, which Node refuses to exec without a shell). The naive fix, `shell:true`, was directly reproduced as UNSAFE (an argv element containing `&&` was genuinely executed as a second shell command; Node's own `DEP0190` deprecation warning confirms this generally). The FIRST real fix wrapped invocations as `cmd.exe /d /s /c <command> <args>` with `shell:false`, verified at the time against `&&`/`||`/`;`/backtick payloads -- a fresh independent Security Reviewer later found and reproduced a REAL, working bypass of this: an argv element containing an embedded double-quote character (e.g. `x" & echo pwned> PWNED.txt & rem "`) broke out of cmd.exe's own re-parsing of the wrapped command line (a different grammar than the C-runtime argv parsing Node's own quoting is correct for) and executed arbitrary cmd.exe syntax, creating a real file on disk. **Fixed with a complete rewrite of `scripts/lib/spawn-platform.mjs`: cmd.exe is never invoked at all.** `resolveWindowsShimTarget()` parses a `.cmd` shim's own content (verified against the real, installed `claude.cmd`/`codex.cmd`) to find the real target it wraps -- a native `.exe`, or `node.exe <script>` -- and invokes that target directly with `shell:false`, which has no re-parsing step to exploit. Any shim not matching the known npm `cmd-shim` shape fails closed (returns `null`); callers must treat that as capability-unavailable and never fall back to the disproven cmd.exe-wrapping approach. Re-verified: the same embedded-double-quote payload no longer creates a file, and live capability detection plus a full live end-to-end worker invocation still succeed. | N/A -- this is the shipped, tested mechanism, not a fallback |

## Documented follow-up

- **Live Codex-side smoke test** (task Section 25/26) remains blocked by this environment's pre-existing, out-of-scope Codex CLI configuration issue -- disclosed, not worked around, and not fixed as part of this checkpoint (outside its scope). The Codex worker direction's mechanics are otherwise identical in design and equally fixture-tested to the now-live-verified Claude direction.
- **Codex-native -> Claude-worker direction cannot obtain real human approval today**, since it inherits ADR-0029's already-shipped deterministic-deny boundary for every `require-approval` class on Codex. This is a disclosed, capability-driven asymmetry identical in kind to the existing Codex `require-approval` asymmetry (`docs/codex-capability-matrix.md`), not a new gap -- see `docs/adr/0030-cross-harness-advisory-workers.md`'s Consequences.
- **`--json-schema`/system-prompt interaction** above is disclosed as a real, reproduced platform behavior on the specific installed version (`2.1.197`), not assumed to generalize to every future version -- worth re-verifying if the pinned Claude Code floor is ever raised.
