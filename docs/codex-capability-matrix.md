- Evidence categories used below, per the checkpoint's own instruction: **locally passed** (real command executed, real output observed), **statically inspected** (source/config read and reasoned about, not executed), **configured but not run** (code exists and is wired, but the specific live scenario was not exercised), **blocked by platform** (this environment cannot exercise it -- no authenticated Codex session, no VS Code instance).

## Documented follow-up (explicitly deferred, not silently missing)

- **Full VS Code project-scoped hook setup -- RESOLVED (`docs/adr/0032-codex-project-scoped-hook-enforcement.md`).** `install-codex.mjs --target hooks` now installs `<repo>/.codex/hooks.json` with dry-run/backup/ownership/rollback and `commandWindows` for every entry (see the table row above for evidence). `--target skill` now also bundles a real, functional runtime (`scripts/`, `references/`, `schemas/`, `policies/`, copied verbatim) so the project-hook launcher has something real to delegate to. The remaining gap is narrower and disclosed precisely: live firing through a real, authenticated Codex session (project-hook trust flow, actual `command`/`commandWindows` invocation by the real binary) is unverified in this environment -- everything short of that (setup mechanics, ownership/merge semantics, and full delegation through to the real enforcement scripts using fixture-copied runtimes) is locally passed.
- **`SessionStart`/`SessionEnd`/`SubagentStart`/`SubagentStop`/`Stop` hooks**: not implemented this checkpoint (see table above for per-event rationale). `PermissionRequest` is implemented in code but not registered (confirmed absent from the installed build's own event enum). None of these gaps weaken the PreToolUse security boundary -- they affect lifecycle bookkeeping/UX polish and defense-in-depth, not the primary enforcement point.
- **Session-id binding for automatic run bootstrapping -- implemented and fixture-verified; end-to-end live operation unverified pending an authenticated session.** The three earlier fix attempts (model-invented placeholder; PreToolUse `allow`+`updatedInput` rewrite, confirmed rejected by the installed binary's own hook-output validation table) both shared the same flawed premise: that the model would have to obtain or carry the session id. That premise was unnecessary. Reverified directly against the official `rust-v0.120.0` source: the `UserPromptSubmit` hook receives the authoritative `session_id` (and `turn_id`/`cwd`/`model`/`permission_mode`/`prompt`) as **required** input fields, before the model ever sees the prompt, and its own output schema genuinely supports `hookSpecificOutput.additionalContext` (unlike PreToolUse, whose rejection table this row previously, correctly, cited -- the two events do not share an output contract). **Shipped:** `scripts/security/user-prompt-submit-codex.mjs` is now the sole place a KRYLO Codex run is *created*; it recognizes only an explicit `$krylo-run` invocation (exact first-token match, inert for every ordinary prompt) and binds the new run directly to the hook-supplied `session_id`, reusing Shared Core's own state functions unchanged. The model never supplies, rewrites, or asserts a session id anywhere in this path. A fresh independent Reviewer and Security Reviewer, dispatched separately, both independently reproduced a real follow-on gap: the Codex CLI adapter (`resolveCodexSessionId`, used by `read-state.mjs`/`update-state.mjs` for calls made AFTER the hook already created a run) had no environment fallback at all, so a session-less CLI call -- exactly what the Skill instructs, mirroring Claude's own Skill -- fell through to the "most recently updated pointer" heuristic and could silently mutate a DIFFERENT concurrent Codex session's run in the same project. Fixed: `resolveCodexSessionId` now falls back to `env.CODEX_THREAD_ID` (the platform-injected shell-execution variable confirmed by `codex-rs/core/src/exec_env.rs` to carry the same underlying `ThreadId` as `session_id`) for this lookup, mirroring `resolveClaudeSessionId`'s existing `env.CLAUDE_SESSION_ID` fallback exactly -- used only to resolve which EXISTING run a later CLI call targets, never to create or bind a run's identity (that stays exclusively the hook's job, using only `payload.session_id`). The same review round also found the four new Codex hook entrypoints (`user-prompt-submit-codex.mjs`, `risk-gate-codex.mjs`, `permission-request-codex.mjs`, `posttool-telemetry-codex.mjs`) were missing from `risk-policy.mjs`'s hook-entrypoint-protection list, letting a model directly invoke `user-prompt-submit-codex.mjs` with fabricated stdin to forge a run bootstrap; fixed by adding all four filenames to that list. Both fixes are regression-tested (`tests/hooks/user-prompt-submit-codex.test.mjs`, `tests/unit/risk-policy.test.mjs`). `$krylo-run` now bootstraps against the verified schema and process-level fixture tests, including the corrected cross-session-isolation behavior; only a live, authenticated firing of the hook on a real Codex session remains unexercised in this environment (see the `UserPromptSubmit` table row above and the CLI row below) -- disclosed as environment-blocked, not claimed as a platform limitation. See `docs/adr/0029`'s "Correction" section for full detail on why the earlier three-attempt conclusion does not hold, and its review-finding addendum for the two follow-on fixes.
- **Live authenticated hook-firing confirmation**: this checkpoint could not run a real, authenticated Codex session in this environment. Every hook script is unit-tested via real subprocess invocation with realistic payloads, and the plugin/hooks/rules files are schema- and Starlark-validated against the real installed binary where a static/non-model-invoking command exists (`codex execpolicy check`) -- but the specific empirical question of whether `codex_hooks`/`features.hooks` actually fires a plugin-bundled hook on this exact installed build (0.120.0) remains open. Do not claim Codex hook enforcement is confirmed live until that test runs.
