# KRYLO Codex Host Capability Matrix

- Checkpoints: `docs/adr/0029-codex-host-packaging-and-approval-boundary.md`, `docs/process/CODEX_HOST_IMPLEMENTATION_PLAN.md`; extended by `docs/adr/0032-codex-project-scoped-hook-enforcement.md`, `docs/process/CODEX_PROJECT_HOOKS_IMPLEMENTATION_PLAN.md`, `docs/adr/0033-codex-lifecycle-enforcement.md`, and `docs/adr/0034-codex-runtime-compatibility-gate.md`; **live-verified for the first time in `docs/adr/0035-codex-live-hook-verification.md`**.
- Installed Codex CLI verified against: `codex-cli 0.120.0` (ADR-0029's original checkpoint; the version this matrix's own historical rows and ADR-0029 both anchor to). Later checkpoints re-verified specific capabilities against newer installed builds where noted inline (`0.152.1` schema re-verification, `0.153.4` CLI management, `0.154.0` live hook firing per ADR-0035/0037/0041) -- those do not replace this anchor, since `codex-compat.mjs`'s own automated drift check (`codex-tested-version-documented`/`codex-tested-version-consistent-with-adr`) cross-references this exact line against ADR-0029's text, and reported `blocked` for a period when this line did not exist in the expected shape (Phase 8, found by actually running the check rather than assuming it still passed).
- Installed Codex CLI in this environment: `codex-cli 0.120.0` (original checkpoint, 2026-08-26). **Current official stable release, independently re-verified 2026-09-02 via a fresh `gh api repos/openai/codex/releases` call (docs/adr/0034, not assumed from any prior checkpoint's own report): `rust-v0.152.1`** (unchanged since the 2026-08-27 check; `0.153.0-alpha.*` exists but is a pre-release, not the stable line) -- a 32-minor-version gap from the installed binary. Every row below marked "re-verified against 0.152.1" was checked directly against that tag's own source (`codex-rs/hooks/...`), not against 0.120.0 or against `main`, per the task's own instruction neither to assume the old baseline nor to trust unreleased `main` behavior. `docs/adr/0034` additionally confirmed, by direct byte-inspection of the installed `codex-cli 0.120.0` binary's own embedded strings, that its recognized hook-event set is exactly `PreToolUse`, `PostToolUse`, `SessionStart`, `UserPromptSubmit`, `Stop` -- **not** `SessionEnd` or `PermissionRequest` -- independently reproducing (not merely repeating) this row's own original finding and directly corroborating the pre-existing, unmodified Ecosystem Maintenance `codex-hook-event-names-recognized` check, which already reports this at `ATTENTION`/`high` severity for `SessionEnd` with zero code change from this checkpoint. Separately, the `codex plugin` CLI management row was re-verified against a newer installed build, `codex-cli 0.153.4` (2026-09-14, see ADR-0029's "Correction" section) -- every other row not explicitly marked as re-verified still reflects only the original 0.120.0 verification.
- **Live verification (2026-09-14, `docs/adr/0035-codex-live-hook-verification.md`) ran against `codex-cli 0.154.0`.** Two Codex CLIs are installed on this machine and they differ: the native installer's (`0.153.4`, what a bare `codex` resolves to interactively) and npm's (`0.154.0`, what KRYLO's own `spawn-platform.mjs` resolution selects and therefore what the compatibility gate probes). Every row marked "fires live" below was observed against `0.154.0` specifically. This divergence is an operational hazard in its own right: a human and KRYLO can be looking at different binaries, so any future contract change must name the exact binary its evidence came from.
- Evidence categories used below, per the checkpoint's own instruction: **locally passed** (real command executed, real output observed), **statically inspected** (source/config read and reasoned about, not executed), **configured but not run** (code exists and is wired, but the specific live scenario was not exercised), **blocked by platform** (this environment cannot exercise it -- originally: no authenticated Codex session and no VS Code instance; as of `docs/adr/0035-codex-live-hook-verification.md` an authenticated session IS available, so remaining blocked-by-platform rows are the ones that need a model turn, which stops at "out of credits", or a real VS Code instance).
- **`codex-cli 0.154.0` is now a REVIEWED, SUPPORTED runtime** (`docs/adr/0038-codex-0154-supported.md`), added on ADR-0037's live evidence via ADR-0034's own amendment procedure. `$krylo-run` bootstraps a normal active run on it, re-verified live with no test override after the edit. `0.120.0` remains supported and untouched; `0.153.4` (a second Codex installed on the same machine) is deliberately still unlisted and therefore still `SAFE_BLOCKED`, since it was never verified. `SessionEnd` is confirmed firing -- an earlier draft recorded it as never firing, which was a misread of `session-end-codex.mjs` no-opping silently on a terminal run.
- **Second live round (2026-09-15, `docs/adr/0037-codex-enforcement-verified-live.md`) closed the post-model-call gap ADR-0035 disclosed.** Observed on `codex-cli 0.154.0`: `PreToolUse` BLOCKS real model-issued commands for both the require-approval and hard-deny classes; a benign command is allowed and executes; `PostToolUse` fires; the Orbit `Stop` gate holds a session open (`hook: Stop Blocked`); and the model reads and obeys the emitted `additionalContext`. Still NOT observed: `SessionEnd` firing (recognized by the binary, never emitted in roughly eight `codex exec` sessions) and the bootstrap-failure marker's own deny path (the model complied with the advisory every time, so no tool call was ever attempted). Also found: **overwriting `config.toml` silently uninstalls the plugin**, since `codex plugin add` stores its registry there -- every hook then stops with no error at all.
- **Hook-event recognition changed since 0.120.0.** Byte-inspection of the installed `codex.exe` (0.154.0) finds EVERY event name present, including `SessionEnd`, `PermissionRequest`, `SubagentStart`/`SubagentStop` and `PreCompact` -- all recorded as absent on 0.120.0 by ADR-0029/0034. This resolves, for current builds, the standing `SessionEnd` registration contradiction. Recognized is weaker evidence than observed, and is marked as such.
- **Third live round (`docs/adr/0041-codex-live-hook-verification-round-two.md`) reached, for the first time, past the post-model-call gap every earlier round disclosed.** `PreToolUse` (both allow and the require-approval deny, with KRYLO's own reason text observed verbatim), `PostToolUse`, `Stop` (both `Blocked` and `Completed` outcomes), and `UserPromptSubmit`'s full loop through a real model turn are now CONFIRMED LIVE, superseding every "fires after the model call, which ADR-0035's sessions never reached" note below for those four events. `SessionEnd` was still never observed firing in any `codex exec` invocation, hook-trust bypass or not -- that specific gap remains open. The same round found and fixed three defects nothing before it had reached: `${PLUGIN_ROOT}` in `SKILL.md` is not resolvable in the model's own shell (only in Codex's own hook-command environment) and every runtime CLI call in the Skill depended on it; fixing that exposed `host-dispatch.mjs`'s `detectHost()` defaulting to `'claude'` in that same shell and silently reading/nearly-overwriting an UNRELATED Claude-host run's state; and the first fix attempt for that (hand the model a literal data-root value) was itself found to be denied outright by KRYLO's own sensitive-path protection, resolved instead by having `resolveCodexDataRoot()` self-derive the value with no input from the model at all. It also confirmed the "Hook trust requirement" row below's open question: hooks beyond `SessionStart` (only `SessionStart` fires without it) require a persisted trust grant `codex exec` cannot establish non-interactively at all, with `--dangerously-bypass-hook-trust` as the only working alternative -- previously recorded as confounded/unconfirmed, now isolated and confirmed as a real, undocumented prerequisite for headless `$krylo-run` usage.

## Documented follow-up (explicitly deferred, not silently missing)

- **Full VS Code project-scoped hook setup -- RESOLVED (`docs/adr/0032-codex-project-scoped-hook-enforcement.md`).** `install-codex.mjs --target hooks` now installs `<repo>/.codex/hooks.json` with dry-run/backup/ownership/rollback and `commandWindows` for every entry (see the table row above for evidence). `--target skill` now also bundles a real, functional runtime (`scripts/`, `references/`, `schemas/`, `policies/`, copied verbatim) so the project-hook launcher has something real to delegate to. The remaining gap is narrower and disclosed precisely: live firing through a real, authenticated Codex session (project-hook trust flow, actual `command`/`commandWindows` invocation by the real binary) is unverified in this environment -- everything short of that (setup mechanics, ownership/merge semantics, and full delegation through to the real enforcement scripts using fixture-copied runtimes) is locally passed.
- **`SubagentStart`/`SubagentStop` hooks**: not implemented this checkpoint (Claude already has these via `scripts/status/agent-events.mjs`; no released-runtime evidence gathered proves either is strictly required for `Stop`/`SessionStart`/`SessionEnd`, and adding them is a separate, reviewable scope per `docs/adr/0033-codex-lifecycle-enforcement.md`). `Stop`/`SessionStart`/`SessionEnd` are now implemented (see table above) -- this row is resolved. `PermissionRequest` is implemented in code but not registered (confirmed absent from the installed build's own event enum). None of these gaps weaken the PreToolUse security boundary -- they affect lifecycle bookkeeping/UX polish and defense-in-depth, not the primary enforcement point.
- **Session-id binding for automatic run bootstrapping -- implemented and fixture-verified; end-to-end live operation unverified pending an authenticated session.** The three earlier fix attempts (model-invented placeholder; PreToolUse `allow`+`updatedInput` rewrite, confirmed rejected by the installed binary's own hook-output validation table) both shared the same flawed premise: that the model would have to obtain or carry the session id. That premise was unnecessary. Reverified directly against the official `rust-v0.120.0` source: the `UserPromptSubmit` hook receives the authoritative `session_id` (and `turn_id`/`cwd`/`model`/`permission_mode`/`prompt`) as **required** input fields, before the model ever sees the prompt, and its own output schema genuinely supports `hookSpecificOutput.additionalContext` (unlike PreToolUse, whose rejection table this row previously, correctly, cited -- the two events do not share an output contract). **Shipped:** `scripts/security/user-prompt-submit-codex.mjs` is now the sole place a KRYLO Codex run is *created*; it recognizes only an explicit `$krylo-run` invocation (exact first-token match, inert for every ordinary prompt) and binds the new run directly to the hook-supplied `session_id`, reusing Shared Core's own state functions unchanged. The model never supplies, rewrites, or asserts a session id anywhere in this path. A fresh independent Reviewer and Security Reviewer, dispatched separately, both independently reproduced a real follow-on gap: the Codex CLI adapter (`resolveCodexSessionId`, used by `read-state.mjs`/`update-state.mjs` for calls made AFTER the hook already created a run) had no environment fallback at all, so a session-less CLI call -- exactly what the Skill instructs, mirroring Claude's own Skill -- fell through to the "most recently updated pointer" heuristic and could silently mutate a DIFFERENT concurrent Codex session's run in the same project. Fixed: `resolveCodexSessionId` now falls back to `env.CODEX_THREAD_ID` (the platform-injected shell-execution variable confirmed by `codex-rs/core/src/exec_env.rs` to carry the same underlying `ThreadId` as `session_id`) for this lookup, mirroring `resolveClaudeSessionId`'s existing `env.CLAUDE_SESSION_ID` fallback exactly -- used only to resolve which EXISTING run a later CLI call targets, never to create or bind a run's identity (that stays exclusively the hook's job, using only `payload.session_id`). The same review round also found the four new Codex hook entrypoints (`user-prompt-submit-codex.mjs`, `risk-gate-codex.mjs`, `permission-request-codex.mjs`, `posttool-telemetry-codex.mjs`) were missing from `risk-policy.mjs`'s hook-entrypoint-protection list, letting a model directly invoke `user-prompt-submit-codex.mjs` with fabricated stdin to forge a run bootstrap; fixed by adding all four filenames to that list. Both fixes are regression-tested (`tests/hooks/user-prompt-submit-codex.test.mjs`, `tests/unit/risk-policy.test.mjs`). `$krylo-run` now bootstraps against the verified schema and process-level fixture tests, including the corrected cross-session-isolation behavior; only a live, authenticated firing of the hook on a real Codex session remains unexercised in this environment (see the `UserPromptSubmit` table row above and the CLI row below) -- disclosed as environment-blocked, not claimed as a platform limitation. See `docs/adr/0029`'s "Correction" section for full detail on why the earlier three-attempt conclusion does not hold, and its review-finding addendum for the two follow-on fixes.
