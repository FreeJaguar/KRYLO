## Documented follow-up (explicitly deferred, not silently missing)

- **Full VS Code project-scoped hook setup** (`<repo>/.codex/hooks.json`, with dry-run/backup/ownership/rollback, Windows `commandWindows` verification): `install-codex.mjs` currently ships the standalone-Skill half of the VS Code bridge only. A standalone-Skill-only install is explicitly documented (in the install plan's own `enforcementNote`) as providing no hook enforcement, consistent with the design doc's requirement that KRYLO must not silently downgrade to a weaker autonomous run when enforcement is missing.
- **`SessionStart`/`SessionEnd`/`SubagentStart`/`SubagentStop`/`Stop` hooks**: not implemented this checkpoint (see table above for per-event rationale). `PermissionRequest` is implemented in code but not registered (confirmed absent from the installed build's own event enum). None of these gaps weaken the PreToolUse security boundary -- they affect lifecycle bookkeeping/UX polish and defense-in-depth, not the primary enforcement point.
- **Session-id binding for automatic run bootstrapping -- CLOSED, working feature, host-authoritative.** The three earlier fix attempts (model-invented placeholder; PreToolUse `allow`+`updatedInput` rewrite, confirmed rejected by the installed binary's own hook-output validation table) both shared the same flawed premise: that the model would have to obtain or carry the session id. That premise was unnecessary. Reverified directly against the official `rust-v0.120.0` source: the `UserPromptSubmit` hook receives the authoritative `session_id` (and `turn_id`/`cwd`/`model`/`permission_mode`/`prompt`) as **required** input fields, before the model ever sees the prompt, and its own output schema genuinely supports `hookSpecificOutput.additionalContext` (unlike PreToolUse, whose rejection table this row previously, correctly, cited -- the two events do not share an output contract). **Shipped:** `scripts/security/user-prompt-submit-codex.mjs` is now the sole place a KRYLO Codex run is created; it recognizes only an explicit `$krylo-run` invocation (exact first-token match, inert for every ordinary prompt) and binds the new run directly to the hook-supplied `session_id`, reusing Shared Core's own state functions unchanged. The model never supplies, rewrites, or asserts a session id anywhere in this path; `process.env.CODEX_THREAD_ID` is available only as a non-authoritative diagnostic/consistency signal, never trusted as identity. `$krylo-run` now bootstraps a fully autonomous, enforced Codex run end to end against the verified schema and process-level fixture tests; only a live, authenticated firing of the hook remains unexercised in this environment (see the `UserPromptSubmit` table row above and the CLI row below) -- disclosed as environment-blocked, not claimed as a platform limitation. See `docs/adr/0029`'s "Correction" section for full detail on why the earlier three-attempt conclusion does not hold.
- **Live authenticated hook-firing confirmation**: this checkpoint could not run a real, authenticated Codex session in this environment. Every hook script is unit-tested via real subprocess invocation with realistic payloads, and the plugin/hooks/rules files are schema- and Starlark-validated against the real installed binary where a static/non-model-invoking command exists (`codex execpolicy check`) -- but the specific empirical question of whether `codex_hooks`/`features.hooks` actually fires a plugin-bundled hook on this exact installed build (0.120.0) remains open. Do not claim Codex hook enforcement is confirmed live until that test runs.
- **`codex plugin` CLI subcommands**: absent on the installed 0.120.0 build despite current docs describing them; local plugin installation currently requires the interactive `/plugins` TUI browser, not exercised here.
