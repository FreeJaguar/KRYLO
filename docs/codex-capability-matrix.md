## Documented follow-up (explicitly deferred, not silently missing)

- **Full VS Code project-scoped hook setup** (`<repo>/.codex/hooks.json`, with dry-run/backup/ownership/rollback, Windows `commandWindows` verification): `install-codex.mjs` currently ships the standalone-Skill half of the VS Code bridge only. A standalone-Skill-only install is explicitly documented (in the install plan's own `enforcementNote`) as providing no hook enforcement, consistent with the design doc's requirement that KRYLO must not silently downgrade to a weaker autonomous run when enforcement is missing.
- **`SessionStart`/`SessionEnd`/`SubagentStart`/`SubagentStop`/`Stop` hooks**: not implemented this checkpoint (see table above for per-event rationale). None of these gaps weaken the security boundary (PreToolUse/PermissionRequest, already implemented) -- they affect lifecycle bookkeeping/UX polish, not enforcement.
- **Live authenticated hook-firing confirmation**: this checkpoint could not run a real, authenticated Codex session in this environment. Every hook script is unit-tested via real subprocess invocation with realistic payloads, and the plugin/hooks/rules files are schema- and Starlark-validated against the real installed binary where a static/non-model-invoking command exists (`codex execpolicy check`) -- but the specific empirical question of whether `codex_hooks`/`features.hooks` actually fires a plugin-bundled hook on this exact installed build (0.120.0) remains open. Do not claim Codex hook enforcement is confirmed live until that test runs.
- **`codex plugin` CLI subcommands**: absent on the installed 0.120.0 build despite current docs describing them; local plugin installation currently requires the interactive `/plugins` TUI browser, not exercised here.
